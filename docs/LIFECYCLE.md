# 模块登记、依赖代次与租约

模块管理器仍在 sf-init 用户态进程中，固定十六个登记槽。服务 RPC、并发生命周期事务、自动故障监督和状态迁移尚待实现；本轮只固定登记依赖与账本事务边界。

## 登记与依赖

sfmod_add 的依赖位图只能引用已登记且未卸载的提供者，拒绝高于十六槽的位和空槽。提供者可以尚未 ACTIVE，因此仍可按依赖顺序先登记再启动。登记时记录每个提供者的 generation；消费者只在对应代次 ACTIVE 时启动。

generation 在登记时递增，停止/重新启动同一登记保持 generation。提供者卸载后即使同一槽、相同 ID 被重新登记，也属于新代次，旧消费者不能自动绑定。需要先卸载旧消费者并针对新提供者重新登记；本轮不提供自动依赖迁移。实际进程与端点的重建仍分别使用新 PID、句柄 generation 和私有回复端点。

计数到 UINT32_MAX 后拒绝进一步登记，返回 SF_NO_SPACE，不回绕到零或复用旧 generation。登记失败不修改槽或计数器。SfModule 新增的代次数组仅为管理器内部结构，不改变包、IPC 或内核 ABI。

## 原子租约记账

启动先检查全部提供者代次、ACTIVE 状态与租约加一容量，再改变消费者状态和统一增加各提供者的引用。任意后置提供者不满足条件时，之前提供者计数和消费者状态均保持。

停止仍要求 DRAINING 且消费者自身资源全部释放。再检查所有依赖代次和待扣引用非零，全部通过后统一扣除；损坏或不平衡的账本返回错误，不部分释放。提供者可以正在排空：消费者正确退出后，提供者才有机会完成停止。CANCEL_STOP 不重复增加依赖租约。

这些检查加固用户态管理器的内部 API，当前普通应用尚不能直接操作这些登记/资源计数，不声称宿主构造的计数溢出可以从恶意 IPC 触发。

## 验证边界

独立宿主测试直接链接产品 manager.c，验证相同及不同 ID 的槽位替换、一千次登记回收、同一登记停止/恢复、错误位图、末代次耗尽、多提供者启动失败时无部分增量、停止失败时无部分扣减和资源计数上限。每个正常 VM 启动也执行独立管理器图的实际替换检查，然后继续全系统服务、设备、应用与持久化回归。最终结果以 TESTING.md 和 PROGRESS.md 的完整回归记录为准。
