# 模块登记、依赖代次与租约

模块管理器仍在 sf-init 用户态进程中，固定十六个登记槽。已提供下述 echo 进程死亡监督；服务 RPC、并发生命周期事务、多服务通用健康协议和状态迁移尚待实现；echo 另提供下述有界健康期限。

## 登记与依赖

sfmod_add 的依赖位图只能引用已登记且未卸载的提供者，拒绝高于十六槽的位和空槽。提供者可以尚未 ACTIVE，因此仍可按依赖顺序先登记再启动。登记时记录每个提供者的 generation；消费者只在对应代次 ACTIVE 时启动。

generation 在登记时递增，停止/重新启动同一登记保持 generation。提供者卸载后即使同一槽、相同 ID 被重新登记，也属于新代次，旧消费者不能自动绑定。需要先卸载旧消费者并针对新提供者重新登记；本轮不提供自动依赖迁移。实际进程与端点的重建仍分别使用新 PID、句柄 generation 和私有回复端点。

计数到 UINT32_MAX 后拒绝进一步登记，返回 SF_NO_SPACE，不回绕到零或复用旧 generation。登记失败不修改槽或计数器。SfModule 新增的代次数组仅为管理器内部结构，不改变包、IPC 或内核 ABI。

## 原子租约记账

启动先检查全部提供者代次、ACTIVE 状态与租约加一容量，再改变消费者状态和统一增加各提供者的引用。任意后置提供者不满足条件时，之前提供者计数和消费者状态均保持。

停止仍要求 DRAINING 且消费者自身资源全部释放。再检查所有依赖代次和待扣引用非零，全部通过后统一扣除；损坏或不平衡的账本返回错误，不部分释放。提供者可以正在排空：消费者正确退出后，提供者才有机会完成停止。CANCEL_STOP 不重复增加依赖租约。

这些检查加固用户态管理器的内部 API，当前普通应用尚不能直接操作这些登记/资源计数，不声称宿主构造的计数溢出可以从恶意 IPC 触发。

## 验证边界

独立宿主测试直接链接产品 manager.c，验证相同及不同 ID 的槽位替换、一千次登记回收、同一登记停止/恢复、错误位图、末代次耗尽、多提供者启动失败时无部分增量、停止失败时无部分扣减和资源计数上限。每个正常 VM 启动也执行独立管理器图的实际替换检查，然后继续全系统服务、设备、应用与持久化回归。最终结果以 TESTING.md 和 PROGRESS.md 的完整回归记录为准。

## Echo 进程死亡监督

sf-init 主循环检查受监督 echo PID 的内核任务状态。实际死亡后按已有生命周期路径收回该实例的服务/回复端点，再等待 25 个单调时钟 tick（当前约 250 ms）启动。每个新实例仍重验模块包并获得独立回复端点。启动失败也消耗尝试次数，并在下次退避后重试；清理不确定时进入 BLOCKED，保留资源供显式处理。

最多三次连续自动启动；成功启动本身不清空预算。连续运行至少 1000 tick（当前约十秒）后，下一次故障才获得新预算。因此短时间反复死亡不会无界重启。计时器使用饱和加法，STOPPED/WAITING/STARTING/RUNNING/BLOCKED 转换由独立用户态策略库控制。

stop echo 禁用自动恢复，已经停止时也可明确保持停止。成功的 start echo 重置预算并重新启用监督；显式启动失败保持停止。echo-status 显示状态、已用自动启动次数和 stable 标记；stable=1 表示下次故障会重新获得预算，显示的历史尝试次数尚未清零。echo-crash 是 root 串口诊断，实际终止当前登记的 echo 实例，用来验证死亡与回收路径。

监督覆盖内置 echo 的实际退出/死亡和下述 ping 失败。sf-init 正在执行同步命令时，观察延迟受该命令限制。sf-native 和设备的原有诊断/显式恢复与隔离规则不变，尤其不自动重新授权隔离中的 DMA 设备；没有状态迁移、持久化重启预算或生产服务 SLA 承诺。

## Echo 健康期限与协议检查

运行中的 echo 每隔 100 tick（当前约一秒）接受一次私有端点 ping，回复等待上限 100 ms。普通 echo 调用保留原一秒等待上限。两者共用完整检查：实际发送者 PID、请求 ID、OP_ECHO、status=0、四字节 ping 原文；拥有正确回复能力但返回错误状态或操作码也不能视为成功。

期限或协议失败后，先终止并回收该受监督实例，再进入同一退避/三次尝试预算；不另建一个可绕过预算的健康重启循环。新实例重新设置健康期限，手动停止不继续 ping，也不会因此复活。时钟截止值饱和计算。

echo-hang 通过 root 专用诊断请求使当前进程进入真正的可抢占自旋；echo-bad-reply 令下一次应答返回 SF_DENIED，echo-bad-op 令其返回错误操作码。诊断由模块检查发送者为 root，普通应用没有该服务发送能力。它们用于验证仍存活的故障进程、真实接收超时以及已认证但不合协议的回复，不代替一般故障域和模块语义验证。

检查仍由 sf-init 主循环推进，同步命令可延迟观察；ping 成功只证明该次协议往返。没有为 native、驱动或任意第三方服务启用自动健康/挂起恢复。
