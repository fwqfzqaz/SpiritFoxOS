# 系统分层与运行模型

本文是理解 SpiritFoxOS 的第一入口，回答三个问题：系统的“核心”是什么、其余功能如何组织、`.sfk` 应用依赖什么运行。

## 1. 核心定位

**SpiritFoxOS 只有一个核心：极简的 Core 0 内核。除此之外的一切都是模块。**

- Core 0 只保留机制：地址空间、任务/线程、抢占调度、能力句柄、IPC、设备与中断授权、DMA 隔离。
- 文件系统、持久化、驱动、网络、图形、运行时库、管理器全部以 `.sfmod` 模块运行在 ring 3。
- 所有可执行应用以签名的 `.sfk` 交付，由运行时模块装载并执行。
- 内核不解析路径、ELF、CBOR、包签名、文件系统、网络协议或图形协议。

## 2. 分层模型

```text
+--------------------------------------------------------------+
|  .sfk 应用（hello、diskhello、第三方应用）                    |
+--------------------------------------------------------------+
|  运行时模块  sf-libsf.sfmod（认证运行时，导出 POSIX 子集）      |
+--------------------------------------------------------------+
|  服务模块    sf-init  sf-fs  sf-persist  sf-wm  sf-net ...      |
|  驱动模块    sf-virtio-blk  sf-ahci  sf-nvme  sf-usb  sf-net     |
+--------------------------------------------------------------+
|  Core 0      地址空间 / 任务线程 / 调度 / 能力 IPC / 中断 / DMA   |
+--------------------------------------------------------------+
|  UEFI 固件 → BOOTX64.EFI（校验并装载内嵌内核与启动包）           |
+--------------------------------------------------------------+
```

依赖方向是单向的：

```text
.sfk 应用 → 运行时模块 → 服务/驱动模块 → Core 0
```

应用不能绕过运行时直接调用内核的服务语义；服务模块不能把文件系统、协议或策略重新塞回内核。

## 3. 职责边界

| 层 | 负责 | 明确不负责 |
| --- | --- | --- |
| Core 0 | 页表与地址空间、任务/线程、调度、能力句柄与 IPC、设备/IRQ/MMIO/DMA 授权、异常与 panic | 路径解析、ELF/`.sfk` 解析、CBOR、签名、文件系统、网络协议、图形协议、策略 |
| `sf-init` | 引导、模块生命周期、依赖代次、策略与外壳、命名空间顶层编排 | 具体文件系统实现、磁盘格式、持久化状态机 |
| `sf-fs` | 命名空间、文件对象、SFRFS/SFRWFS 解析、可写文件系统 | 块设备协议细节、驱动寄存器操作 |
| `sf-persist` | 事务卷、A/B 更新、健康确认、回滚、密钥撤销 | 通用文件系统、命名空间 |
| 驱动模块 | virtio-blk、AHCI、NVMe、xHCI、网卡；寄存器与 DMA 操作 | 文件语义、策略、内核内存管理 |
| `sf-libsf` | 应用运行时、有界 POSIX 子集、文件 RPC 客户端 SDK | 全局状态、TLS、多库依赖、完整 POSIX |
| `.sfk` 应用 | 业务逻辑 | 直接操作硬件、绕过能力模型 |

## 4. `.sfk` 如何运行

1. `sf-init` 验证 `.sfk` 的签名、类型、清单与段布局。
2. `sf-init` 请求 `sf-native`/运行时模块生成装载计划，并由 Core 0 独立校验映射与复制。
3. 运行时模块 `sf-libsf.sfmod` 被链接进应用地址空间，提供有界导出集。
4. 应用通过运行时发起文件、进程、时间等请求；运行时再通过能力 IPC 找到 `sf-fs`、`sf-persist` 等服务。
5. 应用退出或运行时死亡时，租约释放、能力回收，服务保持可用。

因此，**SFK 不是直接跑在内核上的二进制格式，而是“运行在模块提供的运行时与服务之上”的应用包**。

## 5. 当前硬上限

“提高系统上限”首先要把上限写清楚、测量出来，再逐项抬高。当前实现的主要上限如下（细节以代码与 [IMPLEMENTATION](IMPLEMENTATION.md) 为准）：

| 维度 | 当前上限 | 所在层 | 提高方向 |
| --- | --- | --- | --- |
| CPU | 最多 8 核；BSP 计时 + LAPIC IPI | Core 0 | x2APIC、更多核心、中断亲和 |
| 任务/线程 | 32 个任务槽、64 个线程 | Core 0 | 按内存预算动态配置，目标 ≥ 256 进程 / ≥ 1024 线程 |
| 物理内存 | 内核页池固定 4096 页（16 MiB）；已验证 128–512 MiB | Core 0 | 覆盖整机 RAM（≥ 4 GiB），按需分页与回收 |
| 能力句柄 | 每任务 32 槽；端点上限 64 | Core 0 | 按任务预算配置，保持有界 |
| IPC | 4168 字节消息（4096 正文字节） | Core 0 | 共享内存承载大消息，保持小消息低延迟 |
| 存储 | 块协议固定 512 B；设备逻辑扇区 512–4096 B | 驱动 + `sf-fs` | 通用可写卷 ≥ 100 GiB、≥ 100k 文件 |
| 只读镜像 | SFRFS2 ≤ 32 MiB、≤ 48 条目、单文件 ≤ 1 MiB | `sf-fs` | 大镜像与更多条目 |
| 可写卷 | SFRWFS1 128–65536 块 × 4 KiB（最大 256 MiB） | `sf-fs` | 更大卷、快照、配额与恢复 |
| 网络 | 8 个连接对象、248 B 载荷、legacy virtio-net | 网络模块 | ≥ 64 连接、IPv6/DNS、现代网卡与 MSI-X |
| 图形 | 单一 `sf-wm` 直写 framebuffer，≤ 64 MiB | `sf-wm` | 客户端 surface 协议、多窗口、文本输入 |
| 应用 | 8 MiB 映像、8 段、32 导入 / 64 导出、单一运行时库 | 运行时 + Core 0 | ABI 1.0、更完整导出集、SDK 与包仓库 |

## 6. 边界规则

1. 内核只保留机制；新增策略优先做成模块。
2. `.sfmod` 是服务与驱动的交付单元；`.sfk` 是应用的交付单元。
3. 每个上限必须有明确数值、错误码、回收路径与测试证据。
4. 提高上限不得破坏已冻结的 ABI、包格式与服务协议；只允许追加并附 ABI 快照审阅。
5. 文档中的服务归属必须与实际进程一一对应。
