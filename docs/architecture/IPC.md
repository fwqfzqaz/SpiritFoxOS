# IPC 容量、撤回与计量

本文件合并原 IPC 句柄上限、排队发送撤回与复制字节计量三份说明，按“容量上限 → 撤回 → 计量”的顺序描述当前 IPC 的运行期边界。协议主体仍见 [实现边界与 ABI](IMPLEMENTATION.md)。

## 每任务内核能力句柄上限

内核仍使用每任务 32 个槽的固定能力表。新增的运行期上限按非空槽的数量计数，可设为 0–32；所有新建及复用任务默认 32，不继承创建者或旧任务的设置。权限为零的引用也占用一个句柄。

### 配置与生效

`SYS_TASK_CAP_LIMIT=21` 仅允许 PID 1，参数为 `(pid, limit, operation)`：`SF_LIMIT_QUERY=0` 要求 limit 为 0，返回当前上限；`SF_LIMIT_SET=1` 设置并返回新上限。pid 必须为规范的 1..INT32_MAX，目标仍为 READY 或 BLOCKED。高位别名、非法操作/上限拒绝；死亡或空任务返回 NOT_FOUND，普通应用的查询和设置均为 DENIED。

降低到当前占用数量以下返回 BUSY，整个设置保持。成功的设置不关闭、移动或撤销既有句柄，不改变优先级、等待时间或任务状态。计数不按槽位前缀限制：只剩一个高编号槽时可设为 1，该句柄仍可使用和关闭。可用容量还受到物理槽位与代次退休约束，提高上限不会恢复旧句柄。

新建端点、派生句柄和进程创建时授予句柄共用同一准入检查。配额或可用槽不足时返回 NO_SPACE；端点创建在修改全局拥有者、epoch 或队列之前检查本地容量，反复拒绝不占用端点池。共享端点的最后引用、撤销、接收唤醒和进程回收语义保持。关闭/撤销不要求额外配额，也不因当前上限而禁止释放资源。

受信任串口 shell 提供 `cap-limit <pid> [0..32]`。零上限只可设置给没有现存句柄的任务；初始管理器通常持有多个服务端点，`cap-limit 1 0` 会返回 BUSY。查询/提高上限直接走系统调用，不要求先创建 IPC 句柄。设置只从成功调用后生效，不为任务创建增加原子预算参数，也不驱逐已占用的资源。

这是内核能力句柄配额。命名空间文件描述、页面、CPU、线程、消息数量和全局端点池是不同资源；本轮没有把它们合并计费，也不把 APP 的映像内存声明解释为这些配额。清单 requested_caps 计能力名称请求，不等于已占用内核句柄数，也不会自动设置此上限；清单与自动策略配置仍按各自约定处理。

### 验证

`SF_LIMIT_USED=2` 要求 limit 参数为 0，返回活任务当前占用的非空能力槽数量 0–32；SDK 为 `sf_task_cap_usage(pid)`。它沿用 PID 1 权限与规范 PID 检查，不修改能力表、配额、代次、任务状态或调度时间。零权限引用和高编号槽均计数；普通应用也不能查询自己的占用。该查询是调用时的数量快照，不提供预留或跨调用原子操作。

shell 同时显示 `limit=... used=...`，上限与占用分别读取；不能据占用快照推断随后降低一定成功，仍以 SET 的 BUSY/成功结果为准。新增实际控制检查与分阶段 VM 核对继承 2、占满 3、关闭后 2 及退出后 NOT_FOUND。完整状态见 PROGRESS，以下为已交付配额轮次的历史验证。

4014 项实际 core 控制检查包含 1000 个独立占用位图、BUSY/无副作用、0 上限、权限/高位、阻塞状态保持和槽复用默认值。55043 项产品 IPC 检查包含 1000 组增长/占满/拒绝/关闭轨迹，检查创建/派生/授予、高编号槽、零权限引用、代次退休、全局端点池及失败时完整状态保持；原 40908 项 IPC 检查不变。

legacy/modern 专项各四次运行分阶段应用：根先设为 3，应用保留两个继承句柄、创建一个私有端点，重复创建/派生拒绝；根验证降为 2 返回 BUSY、全局端点仍可分配。应用关闭额外句柄后，根成功降为 2；应用继续通过既有两个句柄完成只读文件 SDK 调用，退出回收。另验证普通应用不能查询或提高自身上限、优先级/能力宽度及磁盘字节保持。

完整运行状态以 TESTING 与 PROGRESS 为准。ABI 仅新增系统调用和三个常量，前 558 项无删改，当前 562 项；没有新增 wire 结构。

## 撤回尚未投递的发送

`SYS_SEND_CANCEL=22` / `sf_send_cancel(handle, request_id)` 允许持有 SEND 权限的调用者，撤回该端点队列中由自己发送、完整 64 位请求编号相同的全部条目。内核按实际发送者身份匹配，不能借同一端点或相同编号撤回其他任务的消息；编号 0 合法。

系统调用参数为 `(send_handle, request_id, reserved)`，reserved 必须为 0。成功返回移除数量 0–8；未知/重复撤回或请求已交付返回 0。失效、高位别名或缺少 SEND 权限返回 STALE_HANDLE，非法保留参数返回 INVALID，均不修改队列。接收权限、端点创建者身份或额外能力配额不是此操作的条件。

逻辑 FIFO 中未匹配的消息按原顺序保留，完整载荷和原期限保持；环形 head 可以不为 0。操作不修改端点 epoch、能力表、任务状态或优先级，不分配端点/句柄。它与发送、接收、撤销在当前单核内核中串行处理。

### 边界

直接交付给阻塞接收者后，消息已离开队列，即使接收者尚未再次运行也返回 0。撤回不能修改已交付的缓冲、撤销服务副作用、删除回复或中止 DMA。返回正数只说明相应队列条目移除；如果调用者复用了编号，不代表同编号的其他副本没有更早交付。

这不是完整 RPC 取消协议。调用者应保留有效 SEND 句柄并自行管理请求编号与结果；现有文件客户端没有自动调用此接口或清除超时后的错误状态，其“不确定超时不保证无副作用”的约定保持。服务侧在途取消、确认/排空与状态迁移仍为后续工作。

### 验证

25776 项产品 IPC 宿主检查覆盖明确向量和 1000 组独立逻辑 FIFO 轨迹：认证发送者、同编号他人消息保持、0/高位/重复编号、所有物理 head、满队列、首中尾移除、完整载荷与顺序、无匹配状态、权限/高位/保留参数、失效与撤销、不同端点、直接交付后无效及能力表占满时仍可撤回。

legacy/modern 专项各八次运行分阶段应用：在自有端点验证全 64 位编号、0、重复、环绕及交付后返回 0，再通过继承的 SEND-only 管理器能力撤回自己排队的请求。管理器刻意保留同编号的自身消息并不接收应用请求，应用退出后确认自身消息仍在、应用消息已撤回，验证跨发送者隔离。能力宽度、配额、优先级、文件 IPC、回收和磁盘字节保持。

专项/完整状态以 TESTING 与 PROGRESS 为准；生成测试矩阵不等于执行通过。ABI 仅新增 SYS_SEND_CANCEL=22，前 562 项无删改，当前 563 项，没有新 wire 结构。

## IPC 用户复制字节计数

原设计要求测量 IPC 复制开销。`SYS_IPC_STATS=25` 提供启动以来实际成功用户复制的全局累计值；这是计量接口，不改变消息大小或优化传输。当前每次复制完整 `SfMessage`（328 字节），包含固定头部/存储区，不能把计数解释为逻辑 payload 字节或成功业务请求数。

### 接口

系统调用参数为 `(output, size, reserved)`，仅 PID 1 可调用；size 必须等于 24，reserved 必须为 0。成功返回 0，并通过正常 writable-RAM 检查写出固定宽度结构：

```c
typedef struct {
    uint32_t size, version;
    uint64_t send_bytes, receive_bytes;
} SfIpcStats;
```

version 为 `SF_IPC_STATS_VERSION=1`，布局为 little-endian `<IIQQ`，偏移 0/4/8/16，大小 24、对齐 8。SDK 为 `sf_ipc_stats(out)`，shell 为 `ipc-stats`。普通应用首先返回 DENIED，不读取其参数或修改输出；根任务的非法大小/保留字段返回 INVALID，非法或只读输出返回 DENIED。

两个计数独立在 UINT64_MAX 饱和，不回绕，没有重置接口。查询只读取快照，不分配资源、不消耗端点/能力配额，也不计为一次 IPC receive。当前单核内核在同一个系统调用中取得一致快照；这里没有多核同步、每进程计数、延迟或吞吐保证。

### 哪些复制计费

- SEND：有效 SEND 能力通过后，`copy_in` 成功的全部字节计入 send_bytes。之后因消息格式、期限或满队列拒绝，已经发生的复制仍计入。
- RECEIVE：直接交付给阻塞接收者、或从队列交付时，成功 `copy_out` 的全部字节计入 receive_bytes。
- 失效/缺权限的能力、失败的输入/输出复制、没有交付的阻塞/超时不增加对应值。队列内部搬移、撤回、撤销、关闭和丢弃也不是用户复制；撤回不扣除此前已经复制的输入。
- LOG、进程创建/映像复制及统计快照自身不是此处的 IPC 复制，不计入。

队列接收现在检查输出复制结果：失败返回 DENIED，保留队首和顺序，不返回成功或计费。直接交付输出失败保留原有“接收映射发生变化”的 panic 不变量；不把它转换成正常成功。

### 验证状态

10041 项实际产品 IPC 检查以宿主复制事件日志作为独立参照，覆盖 1000 组队列/直接交付/坏格式/期限/满队列/失败复制/撤回/撤销轨迹。128 位累计参照和显式边界验证 64 位饱和；查询保护字节、完整状态不变及直接输出失败 panic 均检查。6001 项实际 core 控制检查覆盖 1000 组大小/保留参数/成功/失败输出，验证完整64位数据、保护区及普通应用先拒绝。

legacy/modern 专项观察真实计数、四次私有往返、只读输出和普通应用拒绝，并保留配额/撤回/文件 IPC、回收和磁盘字节。全局其他流量可能并行增加计数，因此 VM 往返检查至少增加一个完整消息的复制字节；精确事件相等由宿主独立事件参照验证。当前专项/完整执行状态以 PROGRESS 和 TESTING 为准，未完成验证不得作为通过发布。
