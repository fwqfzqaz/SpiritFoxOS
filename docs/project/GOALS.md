# SpiritFoxOS 目标纲要

版本 1.0 · 2026-11-12 · 长期目标与验收的权威定义

## 0. 文档定位

本文件回答三个问题：SpiritFoxOS 最终要做成什么、什么程度算「实用级」、每个阶段用什么证据判定完成。

| 文档 | 职责 |
| --- | --- |
| **GOALS（本文件）** | 最终目标、实用级验收矩阵、阶段阶梯、非目标与架构不变量 |
| [ROADMAP](ROADMAP.md) | 当前 `v0.3` 的执行拆解与 M0–M7 历史基线 |
| [STATUS](STATUS.md) / [PROGRESS](PROGRESS.md) | 当前事实与历史交付记录 |
| [IMPLEMENTATION](../architecture/IMPLEMENTATION.md) / `architecture/*` | 代码的真实行为与边界 |

实现与文档冲突时，以代码和测试为事实来源；目标口径以本文件为准。目标的变更必须显式审阅，不能由单次提交顺带改写。

## 1. 最终目标

把 SpiritFoxOS 从「可演示的微内核原型」推进为**可在真实 x86_64 UEFI 个人计算机上安装、日常完成实际工作、持续升级并在故障后恢复的实用级操作系统**。

「实用级」不是功能清单的长度，而是三个可验证的性质：

1. **可安装、可启动、可恢复**：普通用户能在真机上完成安装、升级与回滚；升级失败不会变砖；数据损坏可诊断、可恢复。
2. **可完成真实工作**：在不依赖另一台操作系统完成日常任务的前提下，完成文本编辑、软件开发、文件管理与网络访问等目标工作负载。
3. **可持续演进**：ABI、包格式、服务协议与文档稳定；第三方能基于 SDK 开发并分发应用；故障可诊断、性能可回归、版本可维护。

一句话验收：**一台受支持的真机，安装后连续 30 天作为主要开发终端使用，不因系统缺陷丢失数据或需要重装；升级与回滚可重复通过。**

## 2. 目标场景与参考硬件

### 2.1 目标场景

| 场景 | 说明 | 优先级 |
| --- | --- | --- |
| S1 个人开发终端 | 终端、编辑器、交叉编译产物运行、文件与网络；主场景 | v1.0 必须 |
| S2 教学与受控边缘设备 | 只读系统盘 + 可写数据盘、远程管理、快速恢复 | v1.0 必须 |
| S3 应急与恢复控制台 | 系统损坏时仍可串口/图形进入并修复数据 | v1.0 必须 |

### 2.2 参考硬件类

v1.0 的支持边界是「参考硬件类 + 经真机验证的具体机型」，不是任意 x86_64 机器：

- x86_64 UEFI（关闭 CSM），≥ 4 核，≥ 4 GiB RAM；
- NVMe 或 AHCI SATA 存储；
- UEFI GOP 线性 framebuffer，≥ 1920×1080；
- USB 键盘/鼠标，板载有线网卡；
- 可选 Intel VT-d / AMD-Vi。

每种进入支持矩阵的机型必须有可重复的真机测试记录；不在矩阵中的硬件只承诺「可能启动」，不承诺可用。

### 2.3 非目标（v1.0 前明确不做）

- Linux/Windows 二进制兼容、完整 POSIX 系统调用兼容或通用 ELF 动态链接（Linux 兼容按 [规划](../specs/linux-compat/spec.md) 作为 v1.x 可选轨道 G5 推进，不进入 v1.0 验收矩阵）；
- 3D/GPU 加速、游戏、浏览器、完整办公套件；
- 服务器虚拟化、多租户云、容器编排；
- ARM/RISC-V 等第二架构（协议保持可移植，但不列为 v1.0 门槛）；
- Wi-Fi、蓝牙、打印、音频（列为 v1.x 可选）；
- 系统内自举编译工具链（列为 v1.x 目标）；
- 未经验证的「通用硬件支持」承诺。

## 3. 实用级验收矩阵

下表是 v1.0 的完成定义。初版中的时间与吞吐是**初始预算**：`v0.4` 用参考硬件校准，`v0.6` 冻结为回归门；冻结后只允许通过显式审阅调整。

| 维度 | v1.0 验收标准 | 最低证据 |
| --- | --- | --- |
| 启动与安装 | 真机 UEFI 安装到 NVMe/SATA：分区、格式化、写入系统、建立引导项、首次启动进入图形会话；A/B 升级与失败自动回滚；恢复控制台可用；无已知变砖路径 | E3 + E4 |
| CPU 与平台 | ≥ 4 核 SMP 稳定；x2APIC、中断亲和、关机/重启、RTC 时间正确；≥ 4 GiB 物理内存可用 | E3 + E4 |
| 设备与隔离 | USB xHCI 键盘/鼠标/存储热插拔；AHCI/NVMe；GOP framebuffer；MSI/MSI-X 或 INTx；IOMMU 可用时默认隔离全部 DMA，无 IOMMU 时显式降级并告警 | E3 |
| 存储与数据 | 通用可写文件系统：≥ 100 GiB 卷、≥ 100k 文件、权限/配额/原子重命名/fsync；≥ 1000 次随机掉电注入后可通过 fsck 且已提交数据不丢；磁盘错误可诊断、可恢复 | E2 + E3 + E4 |
| 应用与开发接口 | ABI 1.0 冻结；认证运行时库导出集覆盖文件、进程、线程、时间、内存、终端与网络；SDK、模板、示例与文档齐全；第三方可交叉编译、打包、签名、安装并运行 | E1 + E2 + E3 |
| 图形与交互 | 客户端 surface 协议 + 合成器；多窗口、焦点、剪贴板、文本输入；终端模拟器；USB HID 与 PS/2 回退；无图形后端自动回退串口/VNC | E2 + E3 |
| 网络 | IPv4/IPv6、DHCP、DNS、TCP/UDP、socket 风格 API；≥ 64 并发连接；参考硬件上 TCP 吞吐 ≥ 500 Mbps；断网/重连/超时不崩溃 | E3 + E4 |
| 安全与信任 | Secure Boot 信任链（固件 → bootloader → 内核 → 启动包）；密钥轮换与撤销；W^X/NX、PIE 基址随机化、能力最小授权；安全审计无未修复高危问题；有漏洞响应流程 | E3 + 审阅 |
| 可靠性与性能 | 72 小时混合负载 soak 无死锁、无泄漏（内存增长 < 1%）、无永久不可用服务；关键服务崩溃自动恢复；内核 panic 产生可读转储；启动到 shell ≤ 10 s、启动到图形 ≤ 20 s（NVMe 参考硬件）；性能回退 > 10% 阻断合入 | E4 |
| 可维护与生态 | 可复现构建；Linux/Windows CI 全绿；真机硬件 CI ≥ 2 台；包仓库/索引、签名与版本策略可用；升级、降级、撤销可操作；文档与代码同步 | E1–E4 |

### 3.1 证据等级

任何「已支持」「已通过」的表述必须标注证据等级，禁止用低等级证据替代高等级结论：

| 等级 | 含义 |
| --- | --- |
| E1 | 宿主机单元/集成测试或静态审查 |
| E2 | QEMU 端到端场景（含故障注入、负例） |
| E3 | 参考真机上的可重复场景 |
| E4 | 长时间运行、重复掉电/升级、30 天真实使用 |

QEMU 绿色不等于真机结论；真机单次启动不等于长期可靠。

## 4. 架构不变量

以下约束不因短期进度或单个功能需求而放弃；确需变更时必须先修订设计说明并显式审阅。

1. **内核只保留机制**：Core 0 不解析路径、ELF、CBOR、包签名、文件系统、网络协议或图形协议；策略与协议在 ring-3。
2. **驱动与服务用户态化**：设备驱动、文件系统、网络、运行时与合成器均为 `.sfmod`；应用以签名 `.sfk` 交付。
3. **能力最小授权**：所有跨进程资源通过能力句柄传递，支持权利衰减、派生撤销与最后引用回收；不引入绕过能力模型的「后门」。
4. **有界与失败关闭**：新增接口必须有明确的上限、超时、错误码与回收路径；无法确认状态时进入隔离或只读降级，不猜测试探。
5. **接口版本化**：内核 ABI、包格式、服务协议独立版本化；v1.0 前只允许追加并附 ABI 快照审阅，不破坏已验证的包与模块。
6. **单一认证运行时库**：应用导入仍绑定认证的 `sf-libsf.sfmod`；扩展通过受控导出集与用户态库完成，不在内核或应用内复制特权运行时。
7. **证据分级**：每个阶段门禁同时要求宿主、QEMU、真机（适用时）、ABI、文档与 CI；不以单点绿色宣称整体完成。
8. **文档与代码同步**：行为变化同时更新架构文档；阶段完成更新 STATUS/ROADMAP；新增或删除文档更新索引并校验链接。

## 5. 阶段阶梯

阶段编号表示产品成熟度，不表示功能数量。每个阶段只有在退出条件全部满足后才能对外宣称完成。

### G0 · v0.3 模块化收尾与运行时加固（当前）

- **目标**：把「可演示的纵向切片」收敛为边界稳定、可重复验证、可交给他人开发的原型。
- **范围**：`sf-init` 拆分收尾；命名空间/RAMFS 下沉到独立 `sf-fs`；持久化与文件服务生命周期；有界应用接口与 ABI 追加；服务故障注入与降级行为；可启动镜像与真机启动验证。
- **退出条件**：
  - `ROADMAP` 的 v0.3 P0/P1/P2 全部关闭；
  - 全量宿主与 QEMU 回归通过，ABI 只追加并有审阅记录；
  - 至少 1 台参考真机可启动到串口/图形控制台（不要求安装）；
  - 文档中的服务归属与实际进程一一对应。

### G1 · v0.4 真机与数据

- **目标**：从「QEMU 可跑」跨到「真机可装、数据可写、故障可恢复」。
- **范围**：
  - 真机启动矩阵（≥ 2 台，Intel 与 AMD 各一）；framebuffer 控制台；ACPI 关机/重启；RTC。
  - USB xHCI：HID 与存储；AHCI/NVMe 真机验证；MSI/MSI-X 评估与接入。
  - 通用可写文件系统 v1：崩溃一致性、fsck、配额、权限、原子重命名；替换 `5 × 16 KiB` 事务卷作为主存储，保留 A/B 与回滚。
  - 安装器：分区、格式化、写入系统、引导项、首次启动、救援/恢复模式。
  - 内核容量：进程/线程/端点按内存预算可配置（目标 ≥ 256 进程、≥ 1024 线程）；受权服务可创建进程，而非仅 PID 1。
  - 物理内存管理覆盖整机 RAM（≥ 4 GiB），用户页按需分配与回收（不要求 swap）。
- **退出条件**：
  - 2 台真机完成「安装 → 启动 → 关机/重启」并可重复重装；
  - 1000 次掉电注入通过 fsck，已提交数据不丢；
  - 100 GiB 卷、100k 文件、权限与配额场景通过；
  - 证据达到 E3，掉电与重复安装达到 E4。

### G2 · v0.5 工作台

- **目标**：让系统成为可日常操作的工作台，而不是只能运行单个演示应用。
- **范围**：
  - 合成器客户端 surface 协议、多窗口与焦点、剪贴板、文本输入；终端模拟器、编辑器、文件管理器。
  - USB HID 完整化：键盘布局、滚轮、热插拔、输入事件队列；PS/2 回退保留。
  - 网络 v2：IPv6、DNS、socket 风格 API、≥ 64 并发连接、现代网卡与 MSI-X、DHCP 租约与重连。
  - 用户与会话：登录、按用户配额、服务监督与自动重启；包仓库、在线/离线更新与撤销。
  - Secure Boot 信任链与可用的 TPM 度量（硬件具备时）。
- **退出条件**：
  - 在参考真机完成「登录 → 编辑 → 交叉编译 → 运行 → 网络传输 → 关机」闭环；
  - 24 小时混合负载 soak 通过；
  - 升级与回滚在真机重复通过；
  - 证据达到 E3/E4。

### G3 · v0.6 工作负载与可靠性

- **目标**：用真实开发工作负载持续使用，达到「可日常」。
- **范围**：
  - 运行时导出集扩展：线程、时间、进程、终端、环境、文件元数据与网络；TLS 以用户态库提供（可选）。
  - 核心命令行工具与编辑工作流；包工具链、签名与发布流程稳定。
  - 性能：公开 IPC、调度、文件系统、网络基线；CI 性能回归门。
  - 可靠性：72 小时 soak、服务故障注入、内核转储、看门狗与自动恢复。
  - 电源：S3 睡眠/唤醒（目标硬件支持时）、热管理告警。
- **退出条件**：
  - 30 天 dogfood（每天 ≥ 4 小时）无数据丢失、无需重装；
  - 72 小时 soak 通过，性能门生效；
  - 故障注入覆盖所有 ring-3 核心服务；
  - 证据达到 E4。

### G4 · v1.0 实用级发布

- **目标**：发布可被第三方独立安装和使用的 1.0。
- **范围**：
  - 第 3 节验收矩阵全部通过；ABI 1.0 冻结；包格式与服务协议版本化。
  - 发布工程：签名镜像、校验和、升级/回滚、发布说明、支持矩阵、漏洞响应流程。
  - 文档：安装指南、用户手册、SDK、架构说明、故障排查；示例与模板。
- **退出条件**：
  - 2 台以上真机、30 天使用、72 小时 soak、安全检查全部通过；
  - 升级/回滚重复 100 次无变砖；
  - 第三方按文档在受支持硬件上独立完成安装；
  - 所有对外声明均标注证据等级。

### G5 · v1.x 可选轨道：Linux 应用兼容（有界兼容层）

- **目标**：在 v1.0 之后，使受信任包内的 Linux x86_64 程序可在 ring-3 兼容运行时中运行，而不把 ELF、路径或 syscall 语义放进 Core 0。
- **范围**：按 [Linux 兼容规划](../specs/linux-compat/spec.md) 的 S0–S8 推进；首期交付 L1（静态 PIE/musl 命令行程序），L2（动态 musl）为下一里程碑。
- **明确不做**：glibc 动态二进制、`fork`、`ptrace`、`io_uring`、user namespace、X11/Wayland 客户端；不引入 SYSCALL/SWAPGS 门或通用 ELF 动态链接。
- **退出条件**：
  - S1 有界 ELF 装载核心在宿主测试通过，产物可被现有装载校验接受；
  - S2–S5 的兼容入口、syscall 子集、TLS/futex 与动态库装载在 QEMU 正负例通过；
  - 兼容包复用现有签名与认证库信任链，未知 profile 仍被拒绝；
  - 证据等级按 E1/E2/E3 标注，QEMU 绿色不替代真机结论。

G5 不改变 G0–G4 的退出条件与 v1.0 验收矩阵；启用或取消该轨道需按第 8 节单独审阅。

## 7. 与既有阶段的关系

M0–M7 是**纵向切片**，用于组织早期实现，不代表产品完成度：

- M0–M2 提供格式、隔离、能力 IPC 与服务管理基础，对应第 4 节的架构不变量；
- M3–M4 提供文件对象、应用装载与 SDK，对应第 3 节的「应用与开发接口」；
- M5–M6 提供存储、持久化、更新与 DMA 隔离，对应「存储与数据」「安全与信任」；
- M7 提供网络、会话与图形切片，对应「网络」「图形与交互」。

`v0.3` 是 M0–M7 之后的收敛阶段；`v0.4`–`v1.0` 由本文件定义，优先按第 3 节的验收矩阵推进，而不是继续增加互不相连的演示切片。

## 8. 门禁与变更管理

每个阶段、每个对外交付至少满足：

1. 宿主测试 `python3 tools/test.py --host-only` 通过；
2. 涉及内核、ABI、QEMU 行为时完整 `python3 tools/test.py` 通过；
3. 适用时补充真机场景与故障注入，并标注证据等级；
4. ABI 快照只追加并有审阅记录，或在 v1.0 前显式完成冻结评审；
5. STATUS/ROADMAP/对应架构文档与代码同步；
6. Linux 与 Windows CI 均为最新提交通过，不能沿用旧提交的绿色结果。

本文件的阶段名称、验收矩阵与证据等级变更需要独立审阅；阶段内的任务拆分、优先级与实现细节由 [ROADMAP](ROADMAP.md) 维护，可随进展调整。
