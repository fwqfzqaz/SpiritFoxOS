# 路线图：以提高系统上限为方向

更新日期：2026-11-28

## 0. 文档定位

本文件回答“接下来做什么、先做什么、什么算完成”。长期目标与验收口径以 [目标纲要](GOALS.md) 为准，当前事实以 [STATUS](STATUS.md) 和代码为准，逐轮历史证据见 [PROGRESS](PROGRESS.md)。

系统定位只有一句话：**极简 Core 0 是唯一内核，其余功能全部是 `.sfmod` 模块，`.sfk` 应用依托模块提供的运行时与服务运行**。详见 [系统分层与运行模型](../architecture/OVERVIEW.md)。

## 1. 方向：提高系统上限

下一阶段不再以“增加新的纵向演示切片”为主，而是逐项抬高系统的真实上限。所有工作都必须能回答：**抬高了哪一个上限、抬高到多少、用什么证据证明。**

| 上限类别 | 具体含义 | 典型指标 |
| --- | --- | --- |
| 容量上限 | 内核与服务的资源规模 | CPU 核数、进程/线程数、端点/能力数、物理内存、文件数与卷容量 |
| 硬件上限 | 能稳定驱动的真实硬件 | NVMe/AHCI、xHCI、现代网卡、MSI/MSI-X、IOMMU、GOP |
| 性能上限 | 单位时间能完成的工作 | IPC 延迟、启动时间、文件吞吐、TCP 吞吐、调度抖动 |
| 可靠性上限 | 故障与长期运行下的可用性 | 掉电一致性、服务重启、72h soak、升级回滚、内核转储 |
| 生态上限 | 第三方能独立做到什么 | ABI 1.0、SDK、包仓库、签名发布、支持矩阵 |

方向约束：

1. 不把文件系统、协议、策略或图形逻辑重新放进 Core 0。
2. 上限提升优先通过模块与预算配置完成，其次才是内核机制扩展。
3. 每个上限必须有数值、错误码、回收路径、宿主测试与 QEMU/真机证据。
4. 已冻结的 ABI、包格式与服务协议只允许追加，并附 ABI 快照审阅。

## 2. 当前上限基线

| 维度 | 当前 | 下一档目标 | 证据等级 |
| --- | --- | --- | --- |
| CPU | 最多 8 核；QEMU 2 核验证 | ≥ 4 核真机稳定，x2APIC 与中断亲和 | E2 → E3 |
| 任务/线程 | 32 任务槽 / 64 线程 | 按预算配置，≥ 256 进程 / ≥ 1024 线程 | E1/E2 |
| 物理内存 | 内核页池 16 MiB；已验证 128–512 MiB | 覆盖整机 RAM ≥ 4 GiB，按需分配与回收 | E2 → E3 |
| 能力/IPC | 每任务 32 句柄、64 端点、4096 B 正文 | 按任务预算配置；大消息走共享内存 | E1/E2 |
| 存储 | 块协议 512 B；设备扇区 512–4096 B | 通用可写卷 ≥ 100 GiB、≥ 100k 文件 | E2 → E3/E4 |
| 可写卷 | SFRWFS1 最大 256 MiB | 更大卷、配额、快照与恢复 | E1/E2 |
| 网络 | 8 连接、248 B 载荷、legacy virtio-net | ≥ 64 连接、IPv6/DNS、≥ 500 Mbps、现代网卡 | E2 → E3 |
| 图形 | 单一 `sf-wm` 直写 framebuffer | 客户端 surface 协议、多窗口与文本输入 | E2 → E3 |
| 应用 | 8 MiB 映像、单一运行时库、19 项 POSIX 子集 | ABI 1.0、SDK、第三方打包与分发 | E1/E2 → E3 |
| 可靠性 | QEMU 故障注入；SFRWFS 掉电采样 | 1000 次掉电、72h soak、真机升级回滚 | E2 → E4 |

可重复实测入口：`python3 tools/limits.py`（`make limits`）输出声明上限、宿主 IPC/存储基准与 QEMU 启动耗时，明细见 [STATUS](STATUS.md) 第 2.1 节。产品构建默认关闭启动自检（`SF_BOOT_SELFTEST=0`），实测 5.5 s 满足 ≤ 10 s 目标；`make test` 使用测试构建保留全部启动自检。

## 3. 阶段计划

阶段编号表示上限成熟度，不表示功能数量。每个阶段只有退出条件全部满足才能宣称完成。

### U0 · 收敛与度量（当前，对应 GOALS G0）

**目标**：把已有能力收敛为可测量、可回归、可交接的基线，并冻结“内核—模块—SFK”边界。

范围：

- `sf-init` 只保留引导、策略与外壳；命名空间、RAMFS、`/disk` 投影已在 `sf-fs`，继续清理残留耦合。
- 为第 2 节每个上限建立可重复测量：最大任务/线程、内存占用、IPC 延迟、启动时间、文件与网络吞吐。容量、启动、存储与 guest 内 IPC 延迟已由 `tools/limits.py` 覆盖；网络吞吐与图形帧率待补。
- 固化模块归属表：文档中的服务与实际进程一一对应。
- 全量宿主 + QEMU 回归、ABI 快照审阅、Linux/Windows CI 最新提交全绿。

退出条件：

- 上限基线表有实测数字与测试脚本，而不是文档估计（`tools/limits.py` 已覆盖容量/启动/存储/IPC（宿主与 guest）；网络与图形待补）。
- 没有“文档说属于模块、代码却在内核”的例外。
- 至少 1 台参考真机可启动到串口或图形控制台（不要求安装）。

### U1 · 容量上限

**目标**：把固定小上限改为按内存预算配置，使系统能承载真实工作负载。

范围：

- 任务/线程/端点/能力槽从固定值改为启动期预算；目标 ≥ 256 进程、≥ 1024 线程。
- 物理内存管理覆盖整机 RAM（≥ 4 GiB），用户页按需分配与回收；保留无 swap 的有界语义。
- 受权服务可创建进程，而非只有 PID 1 能创建地址空间。
- 内核页池从固定 4096 页改为可配置，并保留失败关闭与回收路径。
- x2APIC、CPU 亲和与中断分发评估。

退出条件：

- 容量压测达到目标值，超出时返回明确错误码而非崩溃。
- 72 小时内高负载无泄漏、无死锁；内存增长 < 1%。
- 证据达到 E1 + E2，真机部分达到 E3。

### U2 · 存储与数据上限

**目标**：让“可写数据”从原型走向可信主存储。

范围：

- SFRWFS1 已把目录创建/删除/改名与目录内文件接入 `/disk`；配额、权限与 fsck 核心已实现，剩余工作是替换 5 × 16 KiB 事务卷作为主存储并补齐安装器路径。
- 卷容量 ≥ 100 GiB、≥ 100k 文件；保持原子重命名与 fsync 语义。
- 1000 次随机掉电注入后 fsck 通过，已提交数据不丢。
- AHCI/NVMe 真机验证；4K 逻辑扇区路径补真机证据。
- 安装器：分区、格式化、写入系统、建立引导项、首次启动与救援模式。

退出条件：

- 2 台真机完成“安装 → 启动 → 写入 → 重启 → 读回”并可重复重装。
- 掉电与恢复达到 E4；数据丢失为零。
- 存储错误可诊断、可降级为只读、可恢复。

### U3 · 硬件与性能上限

**目标**：在参考硬件上稳定运行，并让性能可回归。

范围：

- 真机矩阵 ≥ 2 台（Intel / AMD 各一）；≥ 4 核、≥ 4 GiB RAM、NVMe/AHCI、xHCI HID。
- 网络 v2：IPv6、DNS、socket 风格 API、≥ 64 并发连接、现代网卡与 MSI-X、DHCP 重连。
- 图形：客户端 surface 协议、多窗口、焦点、剪贴板、文本输入；终端模拟器与编辑器。
- 公开 IPC、调度、文件系统、网络性能基线；性能回退 > 10% 阻断合入。
- 启动到 shell ≤ 10 s、启动到图形 ≤ 20 s（NVMe 参考硬件）。

退出条件：

- 参考真机完成“登录 → 编辑 → 交叉编译 → 运行 → 网络传输 → 关机”闭环。
- 性能门进入 CI；真机证据达到 E3。

### U4 · 可靠性与发布上限

**目标**：达到可被第三方独立安装、升级和恢复的发布水平。

范围：

- A/B 升级、失败自动回滚、版本撤销、Secure Boot 信任链与密钥轮换。
- 72 小时混合负载 soak；服务故障自动恢复；内核 panic 可读转储；看门狗。
- ABI 1.0 冻结；SDK、模板、示例与文档齐全；包仓库与签名发布流程稳定。
- 30 天真实使用 dogfood；漏洞响应与支持矩阵。

退出条件：

- 第 3 节验收矩阵全部通过；升级/回滚重复 100 次无变砖。
- 第三方按文档在受支持硬件上独立完成安装与升级。
- 所有对外声明标注 E1–E4 证据等级。

## 4. 优先级与执行顺序

1. **P0 度量与容量**：先建立上限基线，再做 U1 的预算化与内存扩展。
2. **P1 存储与硬件**：U2 与 U3 并行推进；存储可写性是日常使用的硬门槛。
3. **P2 生态与发布**：U4 在 P0/P1 稳定后启动，避免同时扩大边界。

每轮工作遵循以下门禁：

- 宿主测试 `python3 tools/test.py --host-only` 通过；
- 涉及内核、ABI、QEMU 行为时完整 `python3 tools/test.py` 通过；
- ABI 快照仅追加并有审阅记录；
- 文档（STATUS/ROADMAP/对应架构文档）与代码同步；
- Linux 与 Windows CI 均为最新提交通过。

## 5. 历史基线（M0–M7）

M0–M7 是早期纵向切片，用于组织实现，不代表产品完成度。详细证据见 [PROGRESS](PROGRESS.md)。

| 阶段 | 已提供的基础 |
| --- | --- |
| M0 | 容器、CBOR、签名、IPC/BootArgs、打包检查、ABI 快照 |
| M1 | ring 3 隔离、抢占、SMP、线程、能力 IPC、配额 |
| M2 | 依赖代次、租约、受控重启、生命周期 RPC |
| M3 | 命名空间、RAMFS、管道、openat、只读委派、截断 |
| M4 | native 装载、运行时租约、argv/环境、SDK、单一认证运行时库 |
| M5 | virtio-blk、AHCI/NVMe、SFRFS1/SFRFS2、独立 `sf-fs` |
| M6 | 显式写权、双银行事务、A/B、健康确认、VT-d DMA 隔离 |
| M7 | virtio-net、DHCP、IPv4/ICMP/UDP/TCP、账户会话、图形切片 |
