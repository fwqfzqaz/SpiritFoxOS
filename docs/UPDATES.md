# 应用更新试运行与恢复

本阶段只管理一个 native 应用的双槽更新。它在用户态运行，复用 M6 双银行事务，不改变 Core 0 或 EFI 启动槽。包上限 16 KiB，按镜像内有界信任库认证；默认使用独立的应用开发公钥，模块开发公钥默认不能签应用。旧单密钥迁移和扩展应用公钥的重叠轮换/撤销见 `TRUST.md`。

## 使用与状态

```text
install /disk/bin/diskhello.sfk
persist
run installed
persist
```

安装验证签名、应用类型、ABI 1、native 运行时及非空应用身份，再把备用包与 PENDING 状态一起提交。最后一次设备 flush 成功后才返回 `install: COMMITTED`。此时只是待试运行；后续安装返回 BUSY，以免覆盖已确认的回退包。

`run installed` 和 `run /installed.sfk` 使用相同流程：

1. PENDING → TRYING 的记录先完成事务及 flush，才允许装载应用。
2. 选择记录中绑定的包 SHA-256，每次加载验证摘要、签名和 app_id；native 服务再次验证上传的同一快照。
3. 应用在现有 300 tick 截止时间内正常退出且状态为 0，再提交 STABLE，才输出 `update: CONFIRMED` 与 `sfexec: exit 0`。
4. 验证/装载失败、进程异常、非零退出或超时，提交 STABLE 并保留原来的已确认槽，输出 `update: ROLLED BACK`。第一次安装没有已确认槽时回到未安装状态。

PENDING 重启后仍待用户运行。TRYING 表示已尝试但没有持久确认；挂载时先提交回退，再公布 `/persist`，输出 `update: RECOVERED interrupted trial`。正常启动不会自动执行待更新包。已确认应用的后续运行不新增健康度事务。

任何状态事务的写入或 flush 失败均沿用 `SF_COMMIT_UNCERTAIN`，关闭卷准入。运行成功但确认事务失败也返回错误，不能声称更新已确认。重启后可能看到旧记录或完整新记录：TRYING 回退，完整且已确认的 STABLE 保留。恢复提交再次失败时拒绝持久化挂载，不继续尝试执行。

## 选择记录

四个事务键仍是 `/notes/user`、`/slots/a.sfk`、`/slots/b.sfk`、`/boot/current`。最后一个键改为 160 字节的规范记录：

| 字节偏移 | 内容 |
| --- | --- |
| 0–7 | `SFUPD1\0\0` |
| 8 | phase：0 STABLE、1 PENDING、2 TRYING |
| 9 | 已确认槽：0、ASCII a 或 b |
| 10 | 候选槽：0、ASCII a 或 b |
| 11–31 | 全零保留字节 |
| 32–63 | 已确认包 SHA-256；没有槽时全零 |
| 64–95 | 候选包 SHA-256；没有槽时全零 |
| 96–159 | NUL 结尾且尾部补零的 app_id，最长 63 字节 |

app_id 只接受 ASCII 字母、数字、点、下划线和连字符。STABLE 不得有候选；PENDING/TRYING 必须有候选且不同于已确认槽。空状态不得有身份或摘要。未知 phase、非法组合、非零保留或尾部填充均拒绝。

已确认应用存在时，后续候选必须具有相同 app_id。候选包与状态在同一事务提交，试运行固定到该摘要；另一个正确签名包也不能直接替换它。旧版单字节 a/b 记录可读取：先认证所选包，导入为已确认状态，下一次实际升级写入新格式；精确重装仍不写盘。错误的旧包不会被默认信任。

## 已确认版本下限

已安装应用采用有界的数字版本策略：`major.minor.patch`，每段为 0 到 4294967295 的十进制整数；除单个 0 外禁止前导零，不接受前缀、空格、预发布或构建后缀。按三个整数依次比较，`1.2.10` 高于 `1.2.9`。此限制只用于持久化安装及 installed 启动，不改变通用包容器的版本字符串格式。

版本下限来自当前已确认包内的签名清单，先认证包摘要、签名和 app_id 再读取，不添加第二份可能与健康状态不一致的可写计数器：

- 更高版本可提交候选，仍需试运行确认。候选失败或中断时，回退保留旧包及旧下限。
- 更低版本，以及版本相同但包 SHA-256 不同，返回 `SF_VERSION_REJECTED (-21)`。
- 当前已确认包的精确重装输出 `install: UNCHANGED`，不写盘、不切槽、不重新试运行。
- 安装被拒绝不改变卷 generation。确认事务成功后，新的已确认包就是新的下限；确认写/flush 失败仍执行卷的失败关闭及重启恢复规则。

`persist` 显示经认证的 `confirmed-version=... policy=monotonic`；认证失败显示 unavailable 和错误码，不能显示未经认证的版本。执行候选时再次检查版本，以覆盖旧实现留下的 PENDING 记录；不合策略的候选不会执行，按既有健康失败流程回退。

例：`diskhello.sfk` 为 0.1.0，`diskupdate.sfk` 为 0.2.0，`disknext.sfk` 为 0.3.0。安装并确认 0.2.0 后，0.1.0 被拒绝；0.3.0 试运行失败仍允许另一个 0.3.0 候选，健康确认后才拒绝相同版本的不同内容。

## 范围与验证

健康标准是当前有界命令应用的“按时退出 0”，不是长期服务的就绪、业务正确性或生产健康策略。成功确认后的程序在未来一次运行失败，不会自动撤回已确认版本。版本下限只防止持久化安装与 installed 路径的软件降级；直接运行只读盘上另一个包仍是显式独立操作。没有独立可信单调计数、在线信任策略更新、TPM 防回滚、系统/内核双槽或多应用管理。

回退只恢复应用选择器。控制台输出及未来可能加入的文件、网络、数据库副作用不能由选择旧包撤销；本阶段未提供跨应用数据事务或 schema 迁移保证。磁盘摘要不提供离线存储认证；攻击者恢复整份旧磁盘镜像的行为不在此防护范围内。银行损坏后若恢复较早的完整快照，软件版本下限也以该快照中的已确认包为准，不能充当独立硬件防回滚计数器。

`tests/test_update.c` 把实际状态机与事务引擎组合，覆盖 stage/begin/confirm/rollback 四个提交点，各 261 个操作边界 × 三种故障模式，共 3132 个失败场景，并验证恢复记录与槽摘要一致、未确认尝试不能变成已确认版本。规范编码、截断、保留字段、身份、重复试运行和首装失败另有检查。

`tools/qemu_persist_test.py` 在 legacy 和 VT-d/modern 下分别验证实际应用页故障、退出 42、死循环超时、首装失败、待更新保护、身份/摘要/签名拒绝、旧格式迁移、非法状态拒绝、试运行期间终止 QEMU 后回退，以及应用退出 0 后确认写 EIO 不被误报成功。它们不等同于物理断电或任意硬件验收。

`tests/test_version.c` 另有 4069 项检查，覆盖严格数字版本、整数溢出、大小比较、相同版本的摘要约束和 1000 次固定种子往返。QEMU 还覆盖版本确认后重启保持、失败候选不提高下限、幂等重装和拒绝操作字节不变、四种已签名非法版本，以及旧 PENDING 降级/同版本换包/非法版本的启动拒绝。

## 调用预检与待试运行候选

run installed 及 /installed.sfk 别名现在在写 TRYING 前检查 native 登记、进程和服务端点是否可用。runat/runenvat 还对认证有效的候选检查 namespace.read 声明；不支持目录委派的有效应用拒绝本次调用，候选仍保持 PENDING，可用正确形式重试。

| 情况 | TRYING 前处理 | 待执行候选 |
| --- | --- | --- |
| native 停止、排空或死亡 | 返回 STALE_HANDLE、DRAINING 或 DEVICE_GONE | 保留，磁盘不变 |
| 有效包没有 namespace.read，但调用要求目录 | 返回 DENIED | 保留，磁盘不变 |
| 目录不存在、词法/argv/env 非法 | 保持原有预检错误 | 保留，磁盘不变 |
| 候选摘要、签名、身份、版本或清单无效 | 进入既有试运行/装载失败路径 | 回退已确认包 |
| 预检后实际装载/执行失败 | 保持既有健康判定 | 回退已确认包 |

内部 sf_persist_preview 只读认证 PENDING 候选，使用候选槽、候选摘要以及已有版本下限；它不提交状态，也不直接提供执行授权。正常 sf_persist_package 仍拒绝 PENDING，实际装载必须在 TRYING 持久化后重新认证。预检认证错误留给原装载路径处理，避免把坏候选永久留在 PENDING；只有有效包不支持本次调用才提前拒绝。

预检不预留进程/端点/设备资源，也不能保证之后仍可用；后续失败仍按原规则回退。事务格式、版本下限和双槽健康确认协议保持。
