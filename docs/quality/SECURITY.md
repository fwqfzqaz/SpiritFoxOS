# 权限边界审查与修复

日期：2026-10-23。审查基线为 `9a25ac6`，范围包括 Core 0 的用户指针与能力、设备/DMA 生命周期、签名安装与恢复、文件句柄和命名空间。本轮先修复以下已确认缺陷，再执行宿主和真实 VM 回归。

## 已修复问题

| 问题与触发条件 | 影响 | 当前行为与验证 |
| --- | --- | --- |
| modern 驱动把获授的 MMIO 虚拟地址传给 LOG/SEND/RECV | PTE 权限检查把设备页当成普通内存，复制函数会把 BAR 物理地址作为内核指针访问，可能导致 supervisor 异常 | MMIO 页设置独立软件标记，整段缓冲校验拒绝此类页；普通 DMA RAM 仍可复制。真实驱动对四页 LOG/SEND、队列非空与空队列 RECV 做拒绝测试，验证队列消息未被消费 |
| 非特权任务反复创建并关闭端点 | CAP_CLOSE 只清能力槽，泄漏全局端点，活着的任务可耗尽 64 个端点 | 最后一个能力引用关闭时回收端点；派生及其他任务引用仍保持有效；拥有者退出仍撤销端点并唤醒等待者。宿主测试 256 次循环、容量、跨任务引用、撤销、退出与旧句柄；普通应用实际执行 128 次循环 |
| 驱动死亡后访问持久化缓存 | `/persist/notes`、已确认 installed 和状态查询可能继续使用内存快照，错误地报告设备可用 | 持久化准入检查实际任务状态，已打开的读写句柄也失败关闭；设备中途死亡仍能释放 dirty 账本，重新挂载恢复完整已提交数据 |
| 任务退出码为 `SF_BUSY (-7)` | 与原运行标记重合，管理器可能把已死任务当成存活任务，并误判存储可用性 | `SYS_TASK_STATUS` 对活任务返回独立的 `SF_TASK_RUNNING = 0x100000000`，超出所有 int32 退出码范围。普通应用及磁盘驱动退出 -7 的真实负例覆盖等待、缓存拒绝和恢复 |
| 死亡驱动的任务槽已被其他应用复用 | 后续停止旧驱动时找不到旧 PID，导致驱动恢复流程被错误拒绝 | 对已回收 PID 的设备释放返回 NOT_FOUND 时，允许完成服务账本清理；内核设备隔离状态仍独立阻止不安全的新授权。故障后先运行 bundle 应用再恢复磁盘的 VM 路径覆盖该问题 |

另修复扇区写接口的 LBA 乘法回绕：先验证 `lba < capacity/512`，再换算字节偏移。真实事务服务调用验证容量边界与 `(1<<55)+SF_TXN_BANK` 均被拒绝。当前事务引擎只产生固定合法 LBA，没有普通应用可直接调用此内部接口的路径。

持久化挂载在数据和节点准备成功之后才发布回调，失败时保持卷不可用；能力槽达到 generation 上限后跳过该槽，避免一个退休槽阻塞其余容量。

## 返回用户态的防御

新增非 canonical RSP 的返回检查，在 IRET 之前终止该任务，防止处理器在特权返回路径上触发异常。`badrsp.sfk` 刻意设置 `RSP=0x800000000000` 并进入系统调用，验证应用被隔离且回显服务存活。本次 QEMU 在加检查前允许返回并执行到用户 UD2，因此没有把它描述成已在 QEMU 复现的内核崩溃，也没有物理 CPU 验证结论。

任务状态的返回值语义属于当前未冻结 ABI 的修订，当前系统服务与包全部重新构建。调用者必须按 64 位结果比较 `SF_TASK_RUNNING`，不能截断为 32 位或继续把 SF_BUSY 当成存活标记。

## Native 并发装载与相对修正

2026-10-24 并发启动两个应用时复现：已有子进程向共享 manager 端点发送文件请求，装载器等待 native 回复时取走了该请求，因发送者不符拒绝第二次启动，并使原请求失去处理。未复现权限提升或签名绕过；影响是跨请求串扰和可用性。native 改为单独回复端点，仅 manager 和当前 native 持有能力，重启撤销重建。真实启动回归同时创建两个 PI 应用后完成两者 RPC/退出，旧共享通道在该步骤失败，新通道通过。

relative-v1 验证在认证同一不可变快照后进行，最多 256 项，只能写 RW_DATA 完整八字节槽，加数必须在映像实际段内；异常、重复、未对齐、代码/常量目标、间隙、负加数和越界均拒绝。映像应用修正后复制到子进程私有页，两个进程分别修改相同全局初值，BSS 与函数指针均验证。Core 0 独立拒绝栈/BootArgs/DMA 区或未对齐 image_base。精确范围和未实现的导入、TLS、随机化见 NATIVE.md；此修复不代表已提供所有服务的通用消息并发路由。

## 文件分发层的独立边界防御

审查发现分发器依赖传输层的 256 字节约束。进一步核对确认，现有 kernel/ipc.c 在 SYS_SEND 已检查 length<=SF_MSG_BYTES，因此超长文件消息无法通过正常 IPC 到达分发器；没有证据表明存在可利用的越界读写，不能将直接宿主调用的失败宣称为系统漏洞。

新增共享 sf_file_dispatch，在 OP_READ/WRITE/ENUMERATE 调用命名空间前再次检查长度；宿主直接调用不依赖内核前置条件。旧分发代码独立基线首先在 257 字节枚举应拒绝的断言失败，修复后 353 项检查通过，包括保护字节、无副作用、权限和偏移保持。真实 VM 由 rpcprobe 验证内核拒绝超长发送、后续正常消息和只读委派不受影响；该结果与服务级宿主检查分别记录，不混淆验证层级。

## 块设备回复队列串扰

在 `4acbe2f` 基线上加入只用于复现的 channel-test 命令，实际并发启动两个只读目录应用，对冷缓存 readme 执行读取。旧驱动回复与应用请求共用 manager 队列，块 RPC 等待消费了另一应用的请求，后续残留驱动回复又与请求 ID 不匹配，两个应用均以 13 退出。日志 `build/qemu-persist-block-channel-baseline.log`，磁盘字节未变且 VM 可正常关闭；影响为可用性和消息丢失，没有观察到越权读取、错误数据被接受或内核崩溃。

存储层为每个驱动实例创建独立 driver_reply，仅 manager 与当前驱动持有能力，块 RPC 在该端点等待且继续验证发送者和请求 ID。启动失败与正常停止都撤销旧回复端点；停止失败时保留原隔离/失败状态，不把不确定的设备重新授权。native 使用已有独立 runtime_reply，应用文件请求仍由 manager 队列处理，子进程各有独立回复端点。

两种传输的专项 VM 各进行八次并发冷读取、卸载、驱动停止/启动和重新挂载，验证私有回复代次回收、应用/目录引用释放和持久笔记字节不变。这里隔离的是 native 与块设备回复，通用服务并发路由仍待扩展；echo 后续修复如下。

## Echo 实例回复与失败回滚

在块回复已隔离的 `73108a7` 基线上，仅加入 echo-channel-test 复现入口，先启动两个只读应用，再于处理其请求前调用 echo。原 echo_call 在共享 manager 队列中消费了应用请求，结果 e=1/a=2/b=0，日志 `build/qemu-persist-echo-channel-baseline.log`；没有磁盘变化或内核崩溃。

每个 echo 实例现在拥有独立回复端点，EchoPeer 绑定 pid、service、reply；核对 PID/service 后仍验证实际发送者与请求 ID。初始、替换新代、控制台重启和临时磁盘 echo 全部使用该路径，终止后撤销该实例回复端点。新旧代同时存在时也使用不同队列，旧实例不能通过共享回复队列干扰新实例或文件请求。

启动先分配服务端点再分配私有回复；失败会回收已分配对象并将模块状态退回 STOPPED。echo-capacity-test 实际耗尽 root 能力槽，分别触发服务端点与回复端点分配失败，随后释放端点并成功重启。echo-channel-test 在两个冷目录读取进行时同步检查 echo；legacy/modern 各四十次停止/启动与重新挂载检验引用和代次回收，不把这一组固定协议隔离描述成通用并发路由。

## 模块依赖登记复用

原用户态 manager API 仅按槽位保存依赖；停止的消费者在提供者卸载、同槽换成其他模块后仍能重新启动。独立产品 API 基线已复现，现以提供者登记 generation 固定，槽复用后必须重新登记消费者。同一登记的受控停止/重启不改变绑定。计数全量预检同时避免多依赖增减出现部分成功；极限计数由宿主构造验证，当前普通应用没有直接管理器 API，不能把这项结果解释为已复现恶意 IPC 越权。

## Echo 健康与认证回复语义

周期健康检查通过独立实例端点进行，校验发送者、请求 ID、操作码、成功状态和精确载荷。旧正常模块总返回成功且操作码原样，但 echo_call 未独立验证这两个字段；现在真实诊断回复的错误状态/操作码会触发协议失败和同一有界恢复预算，不接受成成功 ping。实际仍存活的自旋进程也会因接收期限触发回收；设备隔离和其他服务的恢复策略保持。没有将受信模块主动返回错误解释为已复现恶意应用越权。

## Native 实例故障与应用租约

运行时故障关闭新启动准入，先终止/撤销旧 native 的两个端点，但保留管理器 DRAINING 登记直至已有应用租约释放。应用使用已复制的私有映像，namespace 请求留在独立 manager 队列；两个真实读取应用在 native 死亡后仍完成并释放引用，再重建新实例。实际能力/进程容量失败验证事务回滚，健康超时和认证协议失败共用有界预算，连续不稳定故障的自动启动受到预算限制，设备 DMA 隔离准入保持。这里不声称一般服务 RPC、状态迁移或物理复位已经完成。

## 进程标识的有符号返回与耗尽

Core 使用 uint32_t next_pid，但 task_new 返回 int。宿主直接包含原 core.c，并替换页表/页帧与硬件机制后，将计数设为 0x80000000：原入口仍创建 READY 任务和十八个模型页，向上层返回负值，计数继续增长。证据 build/task-pid-baseline.txt。继续无界增长还会回绕保留标识。此为根创建路径的边界构造，未在真实 VM 运行二十亿次创建，也不宣称普通应用已能触发。

现在统一取号器只接受 1..INT32_MAX；耗尽或零值失败且计数不变。task_new 在找到空槽后、修改任务/能力/地址空间之前取号；失败不会发布任务，已取号后的后续分配失败仍消耗该标识，避免重用。保留现有 root-only 创建权限与活任务状态哨兵，没有新增修改计数器的 guest 测试接口。

## 已安装调用预检与候选执行屏障

在 8061264 基线上，合法 PENDING 应用没有 namespace.read 时，runat 的 DENIED 发生在 TRYING 之后，导致未执行的有效候选被回退；真实日志 build/qemu-persist-invocation-preflight-baseline.log。现在将有效包的能力不匹配及 native 不可用拒绝放在试运行前，保留候选和磁盘原字节。

只读预览选择候选槽及对应摘要，并认证身份、签名和版本下限。它不是执行入口；普通包读取仍拒绝 PENDING，TRYING 后继续重新认证。坏候选的预览错误不替代原装载失败处理，仍试运行标记并回退。没有改变签名准入、健康确认、版本下限或物理回放限制。

RAM删除保持能力边界：只读委派先返回DENIED，不能通过错误优先级删除或探测忙引用；可写目录的相对请求仍检查经过的只读/挂载节点。跨所有者的打开描述与dup阻止节点回收，关闭后旧generation不会在节点重用时重新生效。本阶段未授予普通应用可写目录，没有实现一般撤销树或持久文件删除。

文件RPC的64位handle过去会窄化为32位再查表。宿主基线build/file-rpc-high-handle-baseline.txt中，(1<<32)|root的CLOSE返回0并关闭自己的有效目录，却因完整64位值不等于Child.root而未清零根；随后OP_ROOT仍返回成功，实际openat却STALE。所有者与generation校验未被越过，不把它描述为跨进程提权。修复在分发入口拒绝所有消费句柄操作的非零高位，后端与根记账均保持；真实隔离应用还验证高位READ/CLOSE被拒绝后正常根、元数据和读取仍可用。

STAT仅序列化显式初始化的32字节记录，原始节点、指针和所有者不进入响应；错误length=0。数据来自现有打开描述与节点，只读授权和设备准入策略保持，缓存元数据不代表设备健康。


## 内核能力整数与扩展 CPU 状态

内核 cap 原接收 uint32_t，却由 64 位 syscall 参数直接传入。真实 ipc.c 的宿主基线复现高位 SEND、CLOSE、DERIVE 和 REVOKE 与调用者自己的合法能力成为别名；没有越过任务归属、epoch、generation 或 rights。现在统一查询保留 uint64_t 并在窄化前拒绝高 32 位，不更改各操作原错误码，非法能力在用户缓冲复制前即失败。

更严重的 CPU 状态基线见 CPU_CONTEXT.md：两个真实签名应用能跨退出读到 XMM0。现在每任务独立 FXSAVE64/FXRSTOR64，任务复用从完整清零状态开始，保留 x87/MMX/SSE 控制及数据；明确禁用未保存的 AVX 配置。最终完整回归通过（1074.85秒、143VM）；覆盖及硬件限制见 CPU_CONTEXT.md。

空目录回收先检查目录能力写权限和当前路径经过的只读/挂载节点；任何所有者的引用或任何后代均阻止回收。检查子树使用路径组件边界，不能因相邻前缀名称误判为空或被占用；根不可能成为规范相对目标。普通应用没有新增写授权，RPC高位和畸形输入不改变命名空间或根记录。

文件客户端在私有回复端点验证实际 PID1、协议、单调编号、操作码及有界返回，异常回复或接收错误后停止该客户端；正常服务错误不毒化。超时不等于取消已入队操作，也不保证没有副作用；丢失的 OPEN 引用可能需要进程回收。SDK 不扩大目录写权限，见 [文件客户端契约](../architecture/FILE_SDK.md)。
