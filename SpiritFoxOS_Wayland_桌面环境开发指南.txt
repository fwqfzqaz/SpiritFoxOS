# 概述与架构总览

本文档为 SpiritFoxOS 移植 Wayland 桌面环境的完整开发路线图，涵盖从内核层到用户态桌面环境的全部技术细节。

## 为什么选择 Wayland 路线

Wayland 是现代 Linux 桌面的显示服务器协议，相比 X11 具有以下核心优势：

- **架构简洁**：去掉了 X 服务器这一中间层，Compositor 直接管理显示输出和输入设备，减少了一层抽象和上下文切换

- **安全性更好**：每个客户端只能看到自己的窗口内容，无法截取其他窗口或监听全局输入事件，从设计上杜绝了键盘记录器和屏幕截取等安全问题

- **性能更优**：直接渲染机制避免了 X11 中的多次数据拷贝，支持垂直同步（vsync）和损伤追踪（damage tracking），减少无效重绘

- **无历史包袱**：X11 积累了 40 年的扩展和遗留代码，Wayland 从零设计，协议清晰简洁

- **移植友好**：对于 SpiritFoxOS 这样的自研内核，Wayland 协议定义清晰，内核接口只需要 DRM/KMS \+ evdev，比移植整个 X\.Org Server 简单得多

**关键认识**：Wayland 本身只是一个协议规范，具体的显示服务由 Compositor 实现。这意味着你可以完全控制窗口管理策略、渲染管线和用户体验，而不是被 X 服务器的设计所束缚。

Wayland 相比传统 X11 具有架构更简洁、安全性更好、性能更优的特点。对于 SpiritFoxOS 这样的自研内核，Wayland 路线意味着更少的历史包袱和更清晰的分层设计。

# 阶段 0：准备工作

## 0\.1 构建系统搭建

移植大量第三方库需要一个可靠的构建系统。推荐使用 **Make \+ 自定义构建脚本** 或 **Meson \+ Ninja** 作为主构建系统。

**推荐方案：分层构建系统**

- **内核层**：继续使用你现有的 Makefile 体系，保持内核构建独立

- **用户态基础库**：使用 Meson \+ Ninja（大多数开源图形库都用 Meson）

- **包管理**：建立类似 ports 的系统，每个第三方库一个构建脚本，自动下载、补丁、配置、编译、安装

**目录结构建议：**

```text
SpiritFoxOS/
├── kernel/              # 内核源码（已有）
├── libc/                # 你的轻量 libc（逐步替换为 musl）
├── userland/            # 用户态程序
│   ├── ports/           # 第三方库移植
│   │   ├── musl/
│   │   ├── libdrm/
│   │   ├── mesa/
│   │   ├── wayland/
│   │   └── ...
│   ├── bin/             # 编译好的二进制
│   ├── lib/             # 编译好的库
│   └── include/         # 头文件
├── sysroot/             # 目标系统根文件系统
│   ├── bin/
│   ├── lib/
│   ├── usr/
│   ├── etc/
│   └── ...
└── tools/               # 构建工具和脚本
    ├── build.sh         # 总构建脚本
    ├── port.sh          # 单个 port 构建工具
    └── env.sh           # 环境变量设置
```

**构建脚本示例（port\.sh）：**

```bash
#!/bin/bash
# port.sh - SpiritFoxOS 第三方库构建工具
# 用法: ./port.sh build libdrm
#       ./port.sh install libdrm

PORT_NAME=$1
PORT_DIR="userland/ports/$PORT_NAME"
SYSROOT="$PWD/sysroot"
PREFIX="/usr"

# 交叉编译环境变量
export CC="x86_64-spiritfoxos-gcc"
export CXX="x86_64-spiritfoxos-g++"
export AR="x86_64-spiritfoxos-ar"
export PKG_CONFIG_SYSROOT_DIR="$SYSROOT"
export PKG_CONFIG_LIBDIR="$SYSROOT/usr/lib/pkgconfig"
export CFLAGS="--sysroot=$SYSROOT -I$SYSROOT/usr/include"
export LDFLAGS="--sysroot=$SYSROOT -L$SYSROOT/usr/lib"

case "$2" in
    build)
        cd "$PORT_DIR"
        ./configure --host=x86_64-spiritfoxos --prefix=$PREFIX
        make -j$(nproc)
        ;;
    install)
        cd "$PORT_DIR"
        make DESTDIR="$SYSROOT" install
        ;;
    clean)
        cd "$PORT_DIR"
        make clean
        ;;
    *)
        echo "Usage: $0 {build|install|clean} port_name"
        exit 1
        ;;
esac
```

## 0\.2 交叉编译工具链

虽然 SpiritFoxOS 运行在 x86\_64 架构上（与宿主系统相同），但为了确保编译出的程序只依赖 SpiritFoxOS 提供的系统调用和库，而不是宿主 Linux 的，仍然需要建立独立的交叉编译工具链。

**方案选择：**

|方案|优点|缺点|推荐度|
|---|---|---|---|
|基于 GCC 自建工具链|完全可控，可定制|工作量大，需要处理 GCC 配置|⭐⭐⭐|
|基于 clang/LLVM|天然支持交叉编译，配置简单|部分程序对 GCC 有依赖|⭐⭐⭐⭐|
|musl\-cross\-make|一键生成 musl 交叉工具链|需要适配 SpiritFoxOS 内核头文件|⭐⭐⭐⭐⭐|

**推荐方案：musl\-cross\-make \+ 自定义内核头文件**

musl\-cross\-make 是一个成熟的 musl 交叉工具链构建脚本，可以快速生成完整的 GCC \+ musl 工具链。你需要做的是：

1. 将 SpiritFoxOS 的内核头文件安装到 sysroot 的 /usr/include 下

2. 修改 musl\-cross\-make 的配置，使用 SpiritFoxOS 的目标三元组（如 x86\_64\-spiritfoxos）

3. 构建工具链，生成 gcc、ld、ar 等工具

4. 验证工具链能正确编译简单程序并在 SpiritFoxOS 上运行

**内核头文件安装：**

你需要为用户态提供一套内核头文件，定义系统调用号、数据结构、ioctl 命令等。建议目录：

```text
sysroot/usr/include/
├── spiritfoxos/       # SpiritFoxOS 特有头文件
│   ├── syscall.h      # 系统调用号定义
│   ├── drm.h          # DRM 接口定义
│   ├── kms.h          # KMS 接口定义
│   └── input.h        # 输入子系统定义
├── sys/               # POSIX 系统头
│   ├── syscall.h
│   ├── ioctl.h
│   └── mman.h
├── linux/             # 兼容 Linux 的头文件（可选）
│   ├── drm.h
│   ├── input.h
│   └── fb.h
└── ...
```

**关键决策**：是否保持 Linux 系统调用 ABI 兼容？你的 README 提到"兼容 Linux x86\-64 ABI"，如果继续保持这个方向，可以直接使用 Linux 的头文件和 musl，大大减少移植工作量。建议保持 Linux ABI 兼容，这样可以直接复用大量现成的 musl 移植工作。

**启动流程设计：**

1. 内核启动，挂载根文件系统（memfs）

2. 挂载 /dev（devfs）、/proc（procfs）、/sys（sysfs）、/tmp（tmpfs）

3. 执行 /sbin/init（初始化进程）

4. init 读取 /etc/fstab，挂载其他文件系统

5. init 启动 udevd（设备管理守护进程）

6. init 启动 D\-Bus 系统总线

7. init 启动显示管理器（或直接启动 compositor）

8. 用户登录后启动 Wayland compositor \+ 桌面环境

**init 系统选择：**

- **简单方案**：写一个简单的 init 程序，按顺序启动服务（适合初期）

- **完整方案**：移植 OpenRC 或 runit（轻量 init 系统）

- **复杂方案**：移植 systemd（功能完整但极其复杂，不推荐初期）

# 阶段 1：内核层 — DRM/KMS 图形子系统

## 1\.1 DRM 子系统核心架构

DRM（Direct Rendering Manager）是 Linux 内核的图形子系统，负责管理 GPU 硬件。它是 Wayland  compositor 与显示硬件之间的内核接口层。

**DRM 子系统核心组件：**

**DRM 核心层职责：**

- **设备管理**：创建 /dev/dri/card0、/dev/dri/controlD64 等设备节点，管理设备生命周期

- **ioctl 分发**：接收用户态 ioctl 调用，分发到各个子模块（KMS、GEM、驱动私有）

- **认证机制**：DRM\-Master 权限管理，控制谁能进行模式设置

- **内存管理**：GEM（Graphics Execution Manager）缓冲区对象管理

- **模式设置**：KMS（Kernel Mode Setting）显示模式配置

**SpiritFoxOS 实现建议：**

你目前的 fb\.c 已经实现了 VBE 帧缓冲和 Bochs VBE DISPI 接口。DRM/KMS 可以在这个基础上扩展：

1. 在 kernel/src/drivers/ 下新建 drm/ 目录

2. 实现 DRM 核心层（设备节点、ioctl 分发、GEM 基础）

3. 实现 KMS 核心层（CRTC、Encoder、Connector、Plane 抽象）

4. 实现 Bochs/QEMU 显示驱动（基于你现有的 VBE 代码）

5. 在 devfs 中注册 DRM 设备节点

**DRM 设备节点：**

|设备文件|用途|权限|
|---|---|---|
|/dev/dri/card0|主渲染设备，用于 GEM 缓冲区和 3D 渲染|所有用户可访问|
|/dev/dri/controlD64|控制设备，用于模式设置|需要 DRM\-Master 权限|
|/dev/dri/renderD128|渲染节点，仅用于计算/渲染，无显示输出|所有用户可访问|

## 1\.2 KMS 模式设置

KMS（Kernel Mode Setting）是 DRM 中负责显示模式设置的部分，它管理显示控制器的硬件资源，包括分辨率、刷新率、颜色深度等。

**KMS 核心对象模型：**

**各对象说明：**

|对象|作用|类比|
|---|---|---|
|**Framebuffer \(FB\)**|显示用的内存缓冲区，包含像素数据|画布|
|**Plane**|图像叠加层，可以独立扫描输出，支持硬件合成|图层|
|**CRTC**|扫描控制器，从帧缓冲读取数据并发送给编码器|播放器|
|**Encoder**|将 CRTC 的数字信号编码为连接器需要的信号格式|转换器|
|**Connector**|物理输出接口（VGA、HDMI、DP 等），连接显示器|接口|

**关键 ioctl 接口：**

```c
// 获取资源信息
DRM_IOCTL_MODE_GETRESOURCES    // 获取 CRTC、Encoder、Connector 数量和 ID

// Connector 操作
DRM_IOCTL_MODE_GETCONNECTOR   // 获取连接器状态（连接/断开、支持的模式）
DRM_IOCTL_MODE_GETPROPBLOB    // 获取属性值（如 EDID）

// CRTC 操作
DRM_IOCTL_MODE_GETCRTC        // 获取 CRTC 当前状态
DRM_IOCTL_MODE_SETCRTC        // 设置 CRTC（绑定 FB、位置、模式）

// 模式设置
DRM_IOCTL_MODE_ADDFB          // 添加帧缓冲
DRM_IOCTL_MODE_RMFB           // 移除帧缓冲
DRM_IOCTL_MODE_DIRTYFB        // 标记帧缓冲脏区域

// 原子模式设置（现代接口）
DRM_IOCTL_MODE_ATOMIC         // 原子性地批量修改多个 KMS 属性
```

**简化实现策略：**

对于 SpiritFoxOS 的 Bochs/QEMU 虚拟显示，初期可以简化实现：

- 1 个 CRTC（只有一个显示控制器）

- 1 个 Encoder（虚拟编码器）

- 1 个 Connector（虚拟显示器）

- 1 个主 Plane（光标 Plane 可选）

- 先实现传统的 SETCRTC 接口，后续再加原子模式设置

**模式设置流程：**

1. 用户态调用 GETRESOURCES 获取资源列表

2. 遍历 Connector，找到已连接的显示器

3. 获取 Connector 支持的模式列表（分辨率、刷新率）

4. 创建 Framebuffer（通过 GEM 缓冲区或 dumb buffer）

5. 调用 SETCRTC 将 Framebuffer 绑定到 CRTC，设置显示模式

6. 显示内容开始扫描输出

## 1\.3 GEM 图形执行管理器

GEM（Graphics Execution Manager）是 DRM 中的图形内存管理器，负责管理 GPU 可访问的缓冲区对象（Buffer Object, BO）。它是 3D 渲染和硬件加速的基础。

**GEM 核心概念：**

- **GEM BO（Buffer Object）**：GPU 可访问的内存缓冲区，是 GEM 的基本管理单元

- **GEM 名称**：32 位整数句柄，用于在进程内引用 GEM BO

- **GEM 全局名称**：跨进程共享的全局名称，用于缓冲区共享

- **mmap 偏移**：用于将 GEM BO 映射到用户态地址空间的偏移量

**关键 ioctl 接口：**

```c
// 缓冲区创建与销毁（驱动特定，这里是 dumb buffer）
DRM_IOCTL_MODE_CREATE_DUMB    // 创建 dumb buffer（CPU 可访问的简单缓冲区）
DRM_IOCTL_MODE_DESTROY_DUMB   // 销毁 dumb buffer
DRM_IOCTL_MODE_MAP_DUMB       // 获取 dumb buffer 的 mmap 偏移

// GEM 通用操作
DRM_IOCTL_GEM_OPEN            // 根据全局名称打开 GEM BO
DRM_IOCTL_GEM_CLOSE           // 关闭 GEM BO 句柄
DRM_IOCTL_GEM_FLINK           // 为 GEM BO 创建全局名称（用于共享）
DRM_IOCTL_PRIME_HANDLE_TO_FD  // GEM BO → DMA-BUF fd（现代共享方式）
DRM_IOCTL_PRIME_FD_TO_HANDLE  // DMA-BUF fd → GEM BO

// 同步操作
DRM_IOCTL_WAIT_VBLANK         // 等待垂直空白
DRM_IOCTL_MODE_PAGE_FLIP      // 页面翻转（异步切换帧缓冲）
```

**Dumb Buffer — 最简实现路径：**

对于初期的软件渲染 Wayland compositor，不需要真正的 GPU 加速，只需要实现 dumb buffer 接口即可：

- Dumb buffer 是 CPU 可直接访问的简单帧缓冲

- 通过 mmap 映射到用户态，用户程序直接写入像素数据

- 不需要 GPU 参与，适合软件渲染（llvmpipe）

- 是 libdrm 测试和 Wayland 软件渲染的最低要求

**Dumb Buffer 实现步骤：**

1. 定义 drm\_gem\_object 结构体（大小、物理地址、虚拟地址、引用计数等）

2. 实现 CREATE\_DUMB ioctl：分配物理连续内存（或散列表），创建 GEM BO

3. 实现 MAP\_DUMB ioctl：返回 mmap 偏移量

4. 实现 mmap 处理：将 GEM BO 映射到用户态地址空间

5. 实现 GEM\_CLOSE：释放 GEM BO 引用

6. 实现 ADDFB：将 GEM BO 包装为 KMS 帧缓冲

**内存分配策略：**

|策略|优点|缺点|适用场景|
|---|---|---|---|
|物理连续页|简单，硬件直接访问|大块分配容易失败|小缓冲区、初期实现|
|散列表 \(SG\)|灵活，利用碎片内存|需要 IOMMU 或硬件支持 SG|大缓冲区、成熟实现|
|预留内存区|可靠，不会碎片化|浪费内存，大小固定|嵌入式、专用 GPU|

**建议**：初期先用物理连续页分配（基于你的物理内存分配器），实现 dumb buffer。等基本功能跑通后，再考虑散列表和真正的 GPU 驱动。

## 1\.4 帧缓冲与 dumb buffer

帧缓冲（Framebuffer）是 KMS 用于显示的内存缓冲区。Dumb buffer 是 DRM 提供的一种简单的、CPU 可访问的缓冲区类型，不需要 GPU 参与。

**Framebuffer 与 GEM BO 的关系：**

- GEM BO 是通用的 GPU 内存缓冲区

- Framebuffer 是绑定了特定格式（宽、高、像素格式、步长）的 GEM BO

- 一个 GEM BO 可以对应多个 Framebuffer（不同格式或视图）

- 只有 Framebuffer 才能被 CRTC 扫描输出

**ADDFB ioctl 参数：**

```c
<code">struct drm_mode_fb_cmd2 {<br/>    __u32 fb_id;           // 输出：创建的 FB ID<br/>    __u32 width;           // 宽度（像素）<br/>    __u32 height;          // 高度（像素）<br/>    __u32 pixel_format;    // 像素格式（四字符码，如 DRM_FORMAT_XRGB8888）<br/>    __u32 flags;           // 标志<br/>    __u32 handles[4];      // GEM BO 句柄（多平面格式用多个）<br/>    __u32 pitches[4];      // 每行字节数（步长）<br/>    __u32 offsets[4];      // 每个平面的偏移<br/>    __u64 modifier[4];     // 格式修饰符（压缩、平铺等）<br/>};
```

**常见像素格式：**

|格式|四字符码|位深|说明|
|---|---|---|---|
|XRGB8888|XR24|32|24 位颜色 \+ 8 位填充（最常用）|
|ARGB8888|AR24|32|带 Alpha 通道|
|RGB565|RG16|16|16 位颜色（低分辨率）|
|XBGR8888|XB24|32|蓝红通道交换|

**页面翻转（Page Flip）：**

页面翻转是实现流畅动画的关键机制：

- **双缓冲**：准备两个帧缓冲，一个显示（front buffer），一个绘制（back buffer）

- **垂直同步**：在 VBlank 期间切换显示的帧缓冲，避免画面撕裂

- **异步通知**：翻转完成后通过事件通知用户态

**页面翻转实现要点：**

1. 实现 DRM\_IOCTL\_MODE\_PAGE\_FLIP ioctl

2. 记录待翻转的目标 FB 和事件上下文

3. 在 VBlank 中断中切换 CRTC 的当前 FB

4. 通过 DRM 事件机制通知用户态翻转完成

5. 用户态收到事件后开始绘制下一帧

## 1\.5 Bochs/QEMU 显示驱动

对于 SpiritFoxOS 的开发测试环境，QEMU/Bochs 虚拟显示是最理想的初始目标。你现有的 fb\.c 已经实现了 Bochs VBE DISPI 接口，可以在此基础上扩展为 DRM 驱动。

**Bochs VBE DISPI 接口回顾：**

你现有的代码已经使用了以下 I/O 端口：

```c
#define VBE_DISPI_IOPORT_INDEX  0x1CE   // 索引端口
#define VBE_DISPI_IOPORT_DATA   0x1CF   // 数据端口

// 寄存器索引
#define VBE_DISPI_INDEX_XRES       0x1  // 水平分辨率
#define VBE_DISPI_INDEX_YRES       0x2  // 垂直分辨率
#define VBE_DISPI_INDEX_BPP        0x3  // 位深
#define VBE_DISPI_INDEX_ENABLE     0x4  // 使能控制
#define VBE_DISPI_INDEX_VIRT_WIDTH 0x6  // 虚拟宽度

// 帧缓冲物理地址
#define VBE_LFB_PHYS_ADDR  0xE0000000   // QEMU 标准 VGA LFB 地址
```

**从 VBE 帧缓冲到 DRM 驱动的迁移路径：**

1. **封装硬件操作**：将现有的 vbe\_set\_mode 等函数封装为驱动层函数

2. **实现 GEM 操作**：基于 LFB 物理地址实现 dumb buffer 创建和映射

3. **实现 KMS 对象**：创建 CRTC、Encoder、Connector、Plane 对象

4. **实现模式设置**：SETCRTC → 调用 vbe\_set\_mode 设置分辨率

5. **实现页面翻转**：通过修改虚拟偏移实现双缓冲（Bochs 支持虚拟宽度大于显示宽度）

6. **注册 DRM 设备**：向 DRM 核心注册驱动，创建设备节点

**双缓冲实现技巧：**

Bochs VBE 支持虚拟宽度大于显示宽度，可以利用这个特性实现双缓冲：

- 设置虚拟宽度 = 实际宽度 × 2（或虚拟高度 = 实际高度 × 2）

- 前缓冲在偏移 0 处，后缓冲在偏移 width 处

- 通过修改 VBE\_DISPI\_INDEX\_X\_OFFSET / Y\_OFFSET 寄存器切换显示起始位置

- 在 VBlank 期间切换，避免画面撕裂

**驱动文件结构建议：**

```text
kernel/src/drivers/drm/
├── drm_core.c          # DRM 核心（设备管理、ioctl 分发）
├── drm_gem.c           # GEM 缓冲区管理
├── drm_kms.c           # KMS 核心（对象管理、模式设置）
├── drm_atomic.c        # 原子模式设置（可选，后期加）
├── bochs_drm.c         # Bochs/QEMU 显示驱动
└── include/
    ├── drm.h           # DRM 公共头文件
    ├── drm_gem.h       # GEM 定义
    ├── drm_kms.h       # KMS 定义
    └── bochs_drm.h     # Bochs 驱动定义
```

**测试验证：**

实现完基本 DRM/KMS 后，可以用 libdrm 的测试程序验证：

- **modetest**：测试 KMS 模式设置，列出所有 KMS 对象

- **kmscube**：OpenGL ES 立方体测试（需要 Mesa）

- **drm\-howto**：简单的 DRM 编程示例

**里程碑**：当 modetest 能正确列出 CRTC、Connector、模式，并能设置模式显示彩色画面时，说明 DRM/KMS 基本实现正确。这是 Wayland 移植的第一个关键里程碑。

# 阶段 2：内核层 — evdev 输入子系统

## 2\.1 输入子系统核心架构

evdev（event device）是 Linux 输入子系统的统一接口，将各种输入设备（键盘、鼠标、触摸板、触摸屏等）抽象为统一的事件流。libinput 和 Wayland compositor 都依赖 evdev 接口。

**输入子系统架构：**

**输入子系统分层：**

- **硬件驱动层**：具体的硬件驱动（PS/2 键盘、USB HID 等），负责从硬件读取原始数据

- **输入核心层**：统一管理输入设备，分发输入事件，维护设备列表

- **evdev 接口层**：将输入事件通过字符设备暴露给用户态，提供统一的事件格式

**SpiritFoxOS 现有基础：**

你已经有了 PS/2 键盘和鼠标驱动（keyboard\.c、mouse\.c），需要做的是：

1. 在现有驱动之上增加输入核心层，统一管理输入设备

2. 实现 evdev 接口层，创建 /dev/input/event\* 设备节点

3. 将 PS/2 键盘和鼠标的事件转换为标准 evdev 事件格式

4. 在 devfs 中注册输入设备节点

**设备节点：**

|设备文件|用途|
|---|---|
|/dev/input/event0|第一个输入设备（通常是键盘）|
|/dev/input/event1|第二个输入设备（通常是鼠标）|
|/dev/input/mice|兼容 PS/2 鼠标协议的混合设备|
|/dev/input/mouse0|第一个鼠标设备|

## 2\.2 evdev 接口实现

evdev 接口通过字符设备向用户态提供输入事件。应用程序通过 read\(\) 系统调用读取事件，通过 ioctl\(\) 查询设备能力和设置属性。

**evdev 设备操作：**

- **open\(\)**：打开输入设备，可以多次打开，每个打开的文件描述符有独立的事件队列

- **read\(\)**：读取输入事件，阻塞式读取，支持非阻塞模式（O\_NONBLOCK）

- **poll\(\)/select\(\)**：等待事件到来，用于事件驱动编程

- **ioctl\(\)**：查询设备信息、设置属性、获取/设置 LED 状态等

- **close\(\)**：关闭设备，释放事件队列

**关键 ioctl 命令：**

```c
// 设备信息查询
EVIOCGVERSION     // 获取 evdev 版本号
EVIOCGID          // 获取设备 ID（总线、厂商、产品、版本）
EVIOCGNAME(len)   // 获取设备名称
EVIOCGPHYS(len)   // 获取设备物理路径
EVIOCGUNIQ(len)   // 获取设备唯一标识

// 能力查询
EVIOCGBIT(ev, len)   // 获取事件类型支持的位图
EVIOCGKEY(len)       // 获取当前按键状态
EVIOCGLED(len)       // 获取当前 LED 状态
EVIOCGSND(len)       // 获取声音状态
EVIOCGSW(len)        // 获取开关状态

// 绝对轴信息
EVIOCGABS(abs)       // 获取绝对轴信息（最小值、最大值、分辨率等）

// 设置操作
EVIOCSKEYCODE      // 设置键码映射
EVIOCSLED          // 设置 LED 状态
EVIOCSSND          // 设置声音状态

// 强制反馈
EVIOCGEFFECTS      // 获取支持的效果数量
EVIOCSFF           // 上传效果
EVIOCRMFF          // 移除效果
EVIOCGBIT(EV_FF, len)  // 获取支持的强制反馈效果
```

**事件队列实现：**

每个 evdev 设备需要维护一个事件队列：

- 环形缓冲区（ring buffer）存储待读取的事件

- 队列满时丢弃最旧的事件（或阻塞，取决于策略）

- 支持多个读者，每个读者有独立的读取位置

- 支持 poll/select，有事件时唤醒等待的进程

**输入核心层数据结构：**

```c
struct input_dev {
    const char *name;           // 设备名称
    const char *phys;           // 物理路径
    struct input_id id;         // 设备 ID

    // 能力位图
    unsigned long evbit[BITS_TO_LONGS(EV_CNT)];     // 支持的事件类型
    unsigned long keybit[BITS_TO_LONGS(KEY_CNT)];   // 支持的按键
    unsigned long relbit[BITS_TO_LONGS(REL_CNT)];   // 支持的相对轴
    unsigned long absbit[BITS_TO_LONGS(ABS_CNT)];   // 支持的绝对轴

    // 绝对轴信息
    struct input_absinfo absinfo[ABS_CNT];

    // 当前状态
    unsigned long key[BITS_TO_LONGS(KEY_CNT)];      // 当前按键状态
    unsigned long led[BITS_TO_LONGS(LED_CNT)];      // 当前 LED 状态

    // evdev 接口
    struct evdev *evdev;

    // 驱动私有数据
    void *private;
};

// 上报输入事件的 API
void input_event(struct input_dev *dev, unsigned int type, 
                 unsigned int code, int value);
void input_report_key(struct input_dev *dev, unsigned int code, int value);
void input_report_rel(struct input_dev *dev, unsigned int code, int value);
void input_report_abs(struct input_dev *dev, unsigned int code, int value);
void input_sync(struct input_dev *dev);
```

## 2\.3 输入事件协议

evdev 使用统一的事件结构来描述所有输入事件。所有输入设备产生的事件都被转换为这种标准格式。

**事件结构体：**

```c
struct input_event {
    struct timeval time;    // 事件发生时间
    __u16 type;             // 事件类型
    __u16 code;             // 事件代码
    __s32 value;            // 事件值
};
```

**事件类型（type）：**

|类型|值|说明|
|---|---|---|
|EV\_SYN|0x00|同步事件，标记一组事件的结束|
|EV\_KEY|0x01|按键/按钮事件（键盘、鼠标按钮等）|
|EV\_REL|0x02|相对轴事件（鼠标移动、滚轮等）|
|EV\_ABS|0x03|绝对轴事件（触摸屏、数位板等）|
|EV\_MSC|0x04|杂项事件|
|EV\_SW|0x05|开关事件（盖子开关、平板模式等）|
|EV\_LED|0x11|LED 事件（键盘 LED 状态）|
|EV\_SND|0x12|声音事件（蜂鸣器等）|
|EV\_REP|0x14|重复事件（按键自动重复）|
|EV\_FF|0x15|强制反馈事件（震动等）|

**同步事件（EV\_SYN）：**

同步事件用于标记一组相关事件的结束：

- **SYN\_REPORT**：报告同步，标记一帧输入事件的结束。例如鼠标移动的 X 和 Y 变化是两个事件，用 SYN\_REPORT 标记它们属于同一帧

- **SYN\_CONFIG**：配置变化同步

- **SYN\_DROPPED**：事件丢失，用户态应该重新查询设备状态

**按键事件（EV\_KEY）：**

- code：键码（KEY\_A、KEY\_ENTER、BTN\_LEFT 等）

- value：1 = 按下，0 = 释放，2 = 自动重复

**相对轴事件（EV\_REL）：**

- code：轴编号（REL\_X、REL\_Y、REL\_WHEEL 等）

- value：相对变化量（有符号整数）

**绝对轴事件（EV\_ABS）：**

- code：轴编号（ABS\_X、ABS\_Y、ABS\_PRESSURE 等）

- value：绝对值（范围由设备能力描述）

**事件帧示例：**

```text
// 鼠标移动到 (100, 200) 并左键按下
type=EV_REL  code=REL_X   value=10     // X 轴移动 +10
type=EV_REL  code=REL_Y   value=-5     // Y 轴移动 -5
type=EV_KEY  code=BTN_LEFT value=1     // 左键按下
type=EV_SYN  code=SYN_REPORT value=0   // 帧结束同步
```

## 2\.4 键盘、鼠标、触摸板驱动

将现有的 PS/2 键盘和鼠标驱动接入输入子系统，是 evdev 实现的第一步。后续可以扩展 USB HID 等更多输入设备。

**PS/2 键盘驱动改造：**

你现有的 keyboard\.c 已经实现了 PS/2 键盘的中断处理和扫描码转换。需要做的改造：

1. 创建一个 input\_dev 结构体，注册到输入核心层

2. 设置键盘的能力位图（支持 EV\_KEY、EV\_LED、EV\_REP 等）

3. 设置支持的按键位图（所有键码）

4. 在键盘中断处理函数中，将扫描码转换为 evdev 键码后，调用 input\_report\_key\(\) 上报事件

5. 每帧事件结束后调用 input\_sync\(\)

6. 实现 LED 控制的回调函数（处理用户态设置 LED 的请求）

**扫描码到 evdev 键码的映射：**

PS/2 键盘使用扫描码（Scan Code Set 1/2/3），evdev 使用统一的键码定义（linux/input\.h 中的 KEY\_\* 常量）。需要建立映射表：

```c
// 简化的扫描码映射表（Set 1）
static const uint16_t scancode_set1[] = {
    [0x01] = KEY_ESC,
    [0x02] = KEY_1,
    [0x03] = KEY_2,
    // ... 更多映射
    [0x1C] = KEY_ENTER,
    [0x1D] = KEY_LEFTCTRL,
    // ...
    [0x3A] = KEY_CAPSLOCK,
    // ...
    [0x4B] = KEY_LEFT,
    [0x48] = KEY_UP,
    [0x4D] = KEY_RIGHT,
    [0x50] = KEY_DOWN,
    // ...
};
```

**PS/2 鼠标驱动改造：**

你现有的 mouse\.c 已经实现了 PS/2 鼠标的中断处理。改造步骤：

1. 创建 input\_dev 结构体，注册到输入核心层

2. 设置鼠标的能力位图（EV\_KEY、EV\_REL）

3. 设置支持的按键（BTN\_LEFT、BTN\_RIGHT、BTN\_MIDDLE）

4. 设置支持的相对轴（REL\_X、REL\_Y、REL\_WHEEL）

5. 在鼠标中断处理函数中，解析鼠标数据包后，调用 input\_report\_rel\(\) 和 input\_report\_key\(\) 上报事件

6. 每帧结束后调用 input\_sync\(\)

**PS/2 鼠标数据包解析：**

```c
// PS/2 鼠标 3 字节数据包
// Byte 0: YV | XV | YS | XS | 1 | MB | RB | LB
// Byte 1: X 位移（低 8 位）
// Byte 2: Y 位移（低 8 位）

void ps2_mouse_handle_packet(uint8_t *data) {
    int x = data[1];
    int y = data[2];

    // 处理符号扩展
    if (data[0] & 0x10) x |= 0xFFFFFF00;  // XS 位
    if (data[0] & 0x20) y |= 0xFFFFFF00;  // YS 位

    // 上报按钮状态
    input_report_key(mouse_dev, BTN_LEFT,   data[0] & 0x01);
    input_report_key(mouse_dev, BTN_RIGHT,  data[0] & 0x02);
    input_report_key(mouse_dev, BTN_MIDDLE, data[0] & 0x04);

    // 上报移动（注意 Y 轴方向）
    input_report_rel(mouse_dev, REL_X, x);
    input_report_rel(mouse_dev, REL_Y, -y);  // PS/2 Y 轴向上为正，evdev 向下为正

    input_sync(mouse_dev);
}
```

**测试验证：**

实现完 evdev 后，可以用以下工具验证：

- **evtest**：列出输入设备并实时显示输入事件

- **libinput debug\-events**：测试 libinput 的事件处理

- **input\-events**：简单的输入事件查看工具

**里程碑**：当 evtest 能正确列出键盘和鼠标设备，并且按键/移动能产生正确的 evdev 事件时，说明输入子系统基本实现正确。这是 Wayland 移植的第二个关键里程碑。

# 阶段 3：用户态基础 — musl libc 移植

## 3\.1 为什么选择 musl

musl libc 是一个轻量级、高质量的 C 标准库实现，专为静态链接和嵌入式系统设计。对于 SpiritFoxOS 这样的自研 OS，musl 是比 glibc 更好的选择。

**musl vs glibc 对比：**

|特性|musl|glibc|
|---|---|---|
|代码规模|约 8 万行 C，简洁紧凑|约 140 万行，庞大复杂|
|静态链接|原生支持，二进制体积小|支持但体积巨大|
|内存占用|低，运行时开销小|高，大量缓存和优化|
|POSIX 兼容性|严格遵循 POSIX，扩展少|POSIX \+ 大量 GNU 扩展|
|线程模型|基于 futex 的简洁实现|复杂的 NPTL 实现|
|移植难度|较低，架构相关代码少|很高，大量平台特定代码|
|许可证|MIT 许可证，更宽松|LGPL，静态链接有传染风险|

**为什么 musl 更适合 SpiritFoxOS：**

- **代码量小**：更容易理解、调试和维护，适合学习和定制

- **架构清晰**：内部模块间耦合度低，更容易适配新的内核

- **系统调用少**：依赖的系统调用比 glibc 少，更容易实现完整支持

- **静态链接友好**：初期可以全部静态链接，简化部署和调试

- **MIT 许可证**：与你的 GPL v3 项目兼容，没有法律风险

**musl 的架构相关代码：**

musl 的代码大部分是架构无关的，架构相关的部分集中在以下目录：

```text
musl/
├── arch/
│   └── x86_64/
│       ├── bits/          # 类型定义、宏（endian.h, setjmp.h 等）
│       ├── syscall_arch.h # 系统调用内联汇编
│       ├── crt/           # 启动代码（crt1.o, crti.o, crtn.o）
│       ├── ldso/          # 动态链接器架构相关代码
│       ├── pthread/       # 线程架构相关代码
│       ├── setjmp.s       # setjmp/longjmp 汇编实现
│       └── longjmp.s
├── src/
│   ├── internal/          # 内部实现（大部分架构无关）
│   ├── stdio/
│   ├── stdlib/
│   ├── string/
│   ├── unistd/
│   ├── pthread/           # pthread 实现（大部分架构无关）
│   ├── ldso/              # 动态链接器（大部分架构无关）
│   └── ...
└── include/               # 头文件（大部分架构无关）
```

**关键认识**：由于 SpiritFoxOS 保持 Linux x86\-64 ABI 兼容，musl 的 x86\_64 架构代码几乎不需要修改。主要工作是：1）确保所有 musl 依赖的系统调用都已实现；2）适配 SpiritFoxOS 的文件系统和设备约定；3）处理一些非标准的行为差异。

## 3\.2 系统调用 ABI 适配

musl 通过 syscall 指令直接调用内核系统调用，不经过任何中间层。系统调用 ABI 的兼容性是 musl 能否运行的关键。

**Linux x86\-64 系统调用 ABI：**

- **系统调用号**：通过 rax 寄存器传递

- **参数**：依次使用 rdi、rsi、rdx、r10、r8、r9（最多 6 个参数）

- **返回值**：rax 寄存器，负值表示错误（\-errno）

- **指令**：syscall 指令（不是 int 0x80）

- **破坏的寄存器**：rcx 和 r11 被 syscall 指令破坏

**musl 系统调用封装：**

musl 使用内联汇编封装系统调用，定义在 arch/x86\_64/syscall\_arch\.h 中：

```c
static inline long __syscall0(long n) {
    unsigned long ret;
    __asm__ __volatile__ ("syscall" : "=a"(ret) : "a"(n) : "rcx", "r11", "memory");
    return ret;
}

static inline long __syscall1(long n, long a1) {
    unsigned long ret;
    __asm__ __volatile__ ("syscall" : "=a"(ret) : "a"(n), "D"(a1) : "rcx", "r11", "memory");
    return ret;
}

// ... __syscall2 到 __syscall6
```

**SpiritFoxOS 需要实现的关键系统调用：**

以下是 musl 强依赖的系统调用，按优先级排序：

**第一优先级（启动必需）：**

- read, write, open, close, fstat, lseek — 基本文件 I/O

- mmap, mprotect, munmap, brk — 内存管理

- exit, exit\_group, getpid — 进程基本

- arch\_prctl — 设置 FS/GS 段基址（TLS 必需）

- set\_tid\_address — 线程 ID 地址（glibc/musl 都需要）

**第二优先级（基本功能）：**

- clone, fork, execve, wait4 — 进程创建与执行

- rt\_sigaction, rt\_sigprocmask, rt\_sigreturn — 信号处理

- futex — 快速用户空间互斥锁（线程同步必需）

- gettimeofday, clock\_gettime, nanosleep — 时间相关

- pipe, dup, dup2, fcntl — 文件描述符操作

- ioctl — 设备控制（终端、DRM 等需要）

- getcwd, chdir, mkdir, rmdir, unlink, rename — 文件系统操作

**第三优先级（完整功能）：**

- epoll 系列 — 事件轮询（网络和 GUI 都需要）

- eventfd, signalfd, timerfd — 事件文件描述符

- inotify 系列 — 文件系统事件监控

- sendfile, splice — 零拷贝 I/O

- prctl, getrlimit, setrlimit — 进程资源控制

- shmget, shmat, shmctl — System V 共享内存

- mmap 的各种标志和属性（MAP\_SHARED, MAP\_ANONYMOUS 等）

**系统调用实现检查清单：**

1. 对照 musl 的 syscall 列表，检查每个系统调用是否已实现

2. 对于未实现的系统调用，返回 ENOSYS（功能未实现）

3. 逐步实现高优先级的系统调用

4. 使用 strace 类工具跟踪程序运行时的系统调用

5. 确保错误码的返回方式符合 Linux ABI（返回值 = \-errno）

**重要**：错误返回方式是常见的坑。Linux 系统调用失败时，返回值是负数，其绝对值是 errno。例如 open 失败返回 \-ENOENT 而不是直接返回错误码。musl 会检查返回值是否在 \-4095 到 \-1 范围内，如果是则设置 errno 并返回 \-1。确保你的系统调用遵循这个约定。

## 3\.3 动态链接器实现

动态链接器（ld\.so）是加载和链接共享库的程序。musl 自带了一个完整的动态链接器实现（ld\-musl\-x86\_64\.so\.1）。

**动态链接器的职责：**

- **程序加载**：读取 ELF 文件，加载程序和依赖的共享库到内存

- **符号解析**：解析未定义的符号，在共享库中查找定义

- **重定位**：修正代码和数据中的地址引用（因为共享库加载地址不固定）

- **初始化**：执行共享库的初始化函数（\.init 段）

- **清理**：程序退出时执行清理函数（\.fini 段）

**动态链接器工作流程：**

1. 内核加载 ELF 文件，识别 PT\_INTERP 段

2. 内核加载动态链接器（ld\-musl\-x86\_64\.so\.1）

3. 内核将控制权交给动态链接器

4. 动态链接器自举（自身重定位）

5. 动态链接器加载主程序和所有依赖的共享库

6. 解析所有符号，执行重定位

7. 执行各库的初始化函数

8. 将控制权交给主程序的入口点（\_start）

**SpiritFoxOS 需要支持的 ELF 特性：**

- ELF64 格式（x86\-64）

- PT\_LOAD 段加载

- PT\_DYNAMIC 动态段解析

- PT\_INTERP 解释器段

- 程序头和节头解析

- 符号表和字符串表

- 重定位表（R\_X86\_64\_RELATIVE, R\_X86\_64\_GLOB\_DAT, R\_X86\_64\_JUMP\_SLOT 等）

**你现有的 ELF 加载器需要补充：**

你现有的 ELF 加载器（kernel/src/fs/elf\.c 或类似）可能只支持静态 ELF。需要补充：

- PT\_INTERP 段支持（识别并加载动态链接器）

- 辅助向量（Auxiliary Vector）传递（AT\_PHDR, AT\_ENTRY, AT\_PAGESZ 等）

- 共享库 mmap 支持（文件映射）

- 更完整的 ELF 解析（动态段、符号表等）

**辅助向量（Auxv）：**

动态链接器需要内核通过栈传递辅助向量，包含程序加载的关键信息：

```c
// 辅助向量类型
#define AT_NULL     0   // 结束标记
#define AT_PHDR     3   // 程序头地址
#define AT_PHENT    4   // 程序头条目大小
#define AT_PHNUM    5   // 程序头数量
#define AT_PAGESZ   6   // 页面大小
#define AT_BASE     7   // 动态链接器加载基址
#define AT_FLAGS    8   // 标志
#define AT_ENTRY    9   // 程序入口点
#define AT_UID      11  // 真实用户 ID
#define AT_EUID     12  // 有效用户 ID
#define AT_GID      13  // 真实组 ID
#define AT_EGID     14  // 有效组 ID
#define AT_CLKTCK   17  // 时钟频率
#define AT_RANDOM   25  // 随机数地址（用于栈保护等）
```

## 3\.4 pthread 线程库

pthread 是 POSIX 线程库，是多线程程序的基础。musl 的 pthread 实现基于 futex 系统调用，简洁高效。

**pthread 依赖的内核支持：**

- **clone 系统调用**：创建新线程（共享地址空间、文件描述符表等）

- **futex 系统调用**：快速用户空间互斥锁（等待和唤醒）

- **set\_tid\_address**：设置线程 ID 地址，线程退出时清零

- **arch\_prctl**：设置 FS 段基址（TLS 线程本地存储）

- **rt\_sigprocmask / rt\_sigaction**：信号掩码和处理（线程级）

- **exit / exit\_group**：线程退出和进程退出

- **munmap**：释放线程栈

**clone 系统调用的 flags：**

创建线程时，clone 需要设置以下标志来共享资源：

```c
// 线程创建的 clone 标志
CLONE_VM          // 共享地址空间（页表）
CLONE_FS          // 共享文件系统信息（cwd, umask 等）
CLONE_FILES       // 共享文件描述符表
CLONE_SIGHAND     // 共享信号处理函数
CLONE_THREAD      // 放入同一个线程组
CLONE_SYSVSEM     // 共享 System V 信号量撤销列表
CLONE_SETTLS      // 设置 TLS（FS 段基址）
CLONE_PARENT_SETTID  // 父进程（创建者）获取 TID
CLONE_CHILD_CLEARTID // 子线程退出时清零 TID 地址
```

**线程本地存储（TLS）：**

x86\-64 上，TLS 通过 FS 段寄存器访问：

- 每个线程有独立的 FS 段基址

- pthread 结构（TCB）位于 FS 段指向的内存中

- 通过 arch\_prctl\(ARCH\_SET\_FS, addr\) 设置 FS 基址

- 线程可以通过 %fs:offset 快速访问线程局部变量

**futex 同步原语：**

futex 是 pthread 同步原语（mutex, cond, sem 等）的内核基础：

```c
// futex 操作
FUTEX_WAIT        // 等待：如果 *uaddr == val，则休眠
FUTEX_WAKE        // 唤醒：唤醒最多 val 个等待者
FUTEX_REQUEUE     // 重排：将等待者从一个 futex 移到另一个
FUTEX_CMP_REQUEUE // 条件重排
FUTEX_WAKE_OP     // 原子操作 + 唤醒
```

**你现有的 futex 实现检查：**

你的 README 提到已经实现了 futex。需要确认：

- FUTEX\_WAIT 是否正确处理了虚假唤醒？

- FUTEX\_WAKE 是否正确唤醒等待队列？

- 是否支持私有 futex（FUTEX\_PRIVATE\_FLAG）？

- 是否支持超时等待（FUTEX\_WAIT\_BITSET）？

**clone 实现要点：**

你的 README 提到实现了 clone。需要确认：

- 是否支持 CLONE\_VM（共享地址空间）？

- 是否支持 CLONE\_THREAD（线程组）？

- 是否支持 CLONE\_SETTLS？

- 线程 ID 和进程 ID 的关系是否正确？

- 信号处理是否按线程组正确分发？

# 阶段 4：图形基础库

## 4\.1 libdrm — DRM 用户态库

libdrm 是 DRM 子系统的用户态库，封装了 DRM ioctl 接口，提供了更友好的编程 API。它是所有图形程序与 DRM 内核交互的基础。

**libdrm 核心功能：**

- **设备管理**：打开/关闭 DRM 设备，获取设备信息

- **模式设置**：封装 KMS 接口，枚举连接器、CRTC、模式，设置显示模式

- **缓冲区管理**：创建/映射/销毁 GEM 缓冲区，dumb buffer 操作

- **事件处理**：VBlank 事件、页面翻转事件的读取和分发

- **驱动特定 API**：各 GPU 厂商的特定接口（Intel、AMD、NVIDIA 等）

**libdrm 主要模块：**

|模块|说明|
|---|---|
|libdrm|核心库，通用 DRM 功能|
|libdrm\-intel|Intel GPU 特定接口|
|libdrm\-amdgpu|AMD GPU 特定接口|
|libdrm\-nouveau|NVIDIA 开源驱动接口|
|libdrm\-radeon|AMD 旧驱动接口|
|libkms|KMS 抽象层（已废弃，建议直接用 DRM API）|

**移植要点：**

- libdrm 主要是 ioctl 的封装，只要内核 DRM 接口兼容 Linux，libdrm 基本不需要修改

- 初期只需要核心库（libdrm\.so），不需要厂商特定的库

- 确保 /dev/dri/card0 设备节点存在且可访问

- dumb buffer 接口是最低要求，必须正确实现

- modetest 是 libdrm 自带的测试工具，用于验证 KMS 功能

**关键 API 示例：**

```c
// 打开 DRM 设备
int fd = drmOpen("bochs", NULL);

// 获取资源
drmModeRes *res = drmModeGetResources(fd);

// 获取连接器
drmModeConnector *conn = drmModeGetConnector(fd, res->connectors[0]);

// 创建 dumb buffer
struct drm_mode_create_dumb create = {0};
create.width = width;
create.height = height;
create.bpp = 32;
drmIoctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &create);

// 映射缓冲区
struct drm_mode_map_dumb map = {0};
map.handle = create.handle;
drmIoctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &map);
void *buf = mmap(0, create.size, PROT_READ | PROT_WRITE, 
                 MAP_SHARED, fd, map.offset);

// 添加帧缓冲
uint32_t fb_id;
drmModeAddFB(fd, width, height, 24, 32, create.pitch, 
             create.handle, &fb_id);

// 设置 CRTC
drmModeSetCrtc(fd, res->crtcs[0], fb_id, 0, 0, 
               &res->connectors[0], 1, &mode);
```

## 4\.2 Mesa — 3D 渲染栈（软件渲染）

Mesa 是开源的 3D 图形栈实现，提供 OpenGL、OpenGL ES、Vulkan 等 API。对于 Wayland 桌面，Mesa 提供硬件加速的 3D 渲染能力。

**Mesa 在 Wayland 中的角色：**

- **EGL 实现**：EGL 是渲染 API（OpenGL ES）与原生窗口系统之间的接口，Wayland 使用 EGL

- **OpenGL/OpenGL ES 实现**：3D 渲染 API

- **GBM 库**：Generic Buffer Manager，通用缓冲区管理器，用于分配 GPU 可访问的缓冲区

- **Wayland EGL 平台**：EGL 的 Wayland 后端，实现 wl\_egl\_window 等接口

**软件渲染（llvmpipe）：**

初期没有 GPU 硬件驱动时，可以使用 llvmpipe（LLVM 管道）软件渲染器：

- llvmpipe 是 Mesa 的软件渲染器，使用 LLVM JIT 编译着色器

- 不需要 GPU 驱动，纯 CPU 渲染

- 性能比硬件加速低，但功能完整，支持 OpenGL 4\.5

- 适合初期开发和调试，确保 Wayland 栈能跑起来

- 后续可以逐步添加真正的 GPU 驱动

**Mesa 核心组件：**

**移植要点：**

- **使用 llvmpipe**：初期只启用 llvmpipe 驱动，不需要 GPU 硬件驱动

- **启用 GBM**：GBM 是 Wayland 必需的缓冲区管理 API

- **启用 EGL**：Wayland 使用 EGL 作为渲染上下文管理 API

- **启用 Wayland 平台**：Mesa 的 EGL 需要 Wayland 平台支持

- **依赖 LLVM**：llvmpipe 需要 LLVM，这是一个较大的依赖

**Meson 配置选项（推荐配置）：**

```bash
meson build \
    -Dplatforms=wayland \
    -Ddri-drivers= \
    -Dgallium-drivers=llvmpipe \
    -Dvulkan-drivers= \
    -Degl=true \
    -Dgbm=true \
    -Dgles1=true \
    -Dgles2=true \
    -Dopengl=true \
    -Dglx=disabled \
    -Dllvm=true \
    -Dshared-llvm=true
```

**优化建议**：如果觉得 LLVM 太大，可以考虑使用 softpipe（更简单的软件渲染器），但 softpipe 功能更弱，性能也更差。llvmpipe 是更好的选择，虽然编译时间长，但功能和性能都好很多。

## 4\.3 FreeType — 字体光栅化

FreeType 是最流行的字体光栅化库，负责将矢量字体（TrueType、OpenType、Type1 等）渲染为位图。它是所有文本显示的基础。

**FreeType 核心功能：**

- **字体加载**：支持 TrueType \(\.ttf\)、OpenType \(\.otf\)、Type 1、CFF、WOFF 等格式

- **字形光栅化**：将矢量字形渲染为位图（抗锯齿、单色、LCD 优化等）

- **字形度量**：获取字形的宽度、高度、基线、间距等度量信息

- **字形索引**：通过字符码查找字形索引

- **高级特性**：Hinting（字形微调）、Kerning（字距调整）、OpenType 特性等

**移植要点：**

- FreeType 是纯 C 库，几乎没有系统依赖，移植非常简单

- 只依赖 libc 和 zlib（用于压缩字体）

- 不需要任何内核支持

- 可以使用 Meson 或 Autotools 构建

**基本使用示例：**

```c
#include <ft2build.h>
#include FT_FREETYPE_H

FT_Library library;
FT_Face face;

// 初始化 FreeType
FT_Init_FreeType(&library);

// 加载字体文件
FT_New_Face(library, "/usr/share/fonts/DejaVuSans.ttf", 0, &face);

// 设置像素大小
FT_Set_Pixel_Sizes(face, 0, 16);

// 加载字形
FT_Load_Char(face, A, FT_LOAD_RENDER);

// 访问位图
FT_Bitmap *bitmap = &face->glyph->bitmap;
// bitmap->buffer: 像素数据
// bitmap->width: 宽度
// bitmap->rows: 高度
// bitmap->pitch: 行字节数
```

## 4\.4 Fontconfig — 字体配置

Fontconfig 是字体配置和匹配库，负责管理系统中的字体文件，并根据应用程序的需求匹配合适的字体。

**Fontconfig 核心功能：**

- **字体发现**：扫描系统中的字体文件，建立字体缓存

- **字体匹配**：根据字体名称、样式、大小等属性匹配合适的字体

- **字体替换**：当请求的字体不存在时，自动替换为类似的字体

- **字体配置**：通过配置文件自定义字体渲染参数、别名、替换规则等

**移植要点：**

- 依赖 FreeType（读取字体信息）和 expat（解析 XML 配置）

- 需要 /etc/fonts/ 目录存放配置文件

- 需要 /usr/share/fonts/ 目录存放字体文件

- 首次运行时需要生成字体缓存（fc\-cache）

- 配置文件是 XML 格式，可以自定义字体匹配规则

**字体目录结构：**

```text
/usr/share/fonts/
├── truetype/         # TrueType 字体
│   ├── dejavu/       # DejaVu 字体族
│   └── ...
├── opentype/         # OpenType 字体
├── type1/            # Type 1 字体
└── ...

/etc/fonts/
├── fonts.conf        # 主配置文件
├── conf.d/           # 配置片段目录
│   ├── 10-hinting.conf
│   ├── 20-fix-globaladvance.conf
│   └── ...
└── fonts.cache-1     # 字体缓存（自动生成）
```

**推荐字体：**

- **DejaVu**：开源字体族，覆盖字符广，适合作为系统默认字体

- **Noto**：Google 开发的开源字体，支持几乎所有语言

- **Liberation**：与 Arial、Times New Roman、Courier New 度量兼容的字体

- **WenQuanYi**：开源中文字体

## 4\.5 HarfBuzz — 文本整形

HarfBuzz 是文本整形（Text Shaping）引擎，负责将 Unicode 文本转换为字形序列，处理复杂的排版规则。

**什么是文本整形？**

对于简单的拉丁文字，每个字符对应一个字形，直接排列即可。但对于复杂文字系统：

- **阿拉伯文**：字符根据位置有不同的字形（初始、中间、末尾、独立）

- **印度文字**：需要复杂的连字和重排规则

- **泰文**：需要正确的元音和声调位置

- **OpenType 特性**：连字（fi, fl）、小型大写字母、旧式数字等

HarfBuzz 负责处理所有这些复杂的排版规则，输出正确的字形序列和位置。

**HarfBuzz 在文本渲染管线中的位置：**

```text
Unicode 文本
    ↓
HarfBuzz（文本整形）
    ↓
字形序列 + 位置信息
    ↓
FreeType（字形光栅化）
    ↓
位图字形
    ↓
合成到帧缓冲
```

**移植要点：**

- HarfBuzz 是纯 C\+\+ 库（但提供 C API），需要 C\+\+ 标准库支持

- 依赖 FreeType（用于加载字体中的字形信息）

- 可以使用 Meson 构建

- HarfBuzz 本身不做光栅化，只做整形，因此不需要内核支持

- 是 Pango、Cairo、Qt、GTK 等库的依赖

**基本使用示例：**

```c
#include <hb.h>
#include <hb-ft.h>

// 创建缓冲区
hb_buffer_t *buf = hb_buffer_create();

// 添加文本
hb_buffer_add_utf8(buf, text, -1, 0, -1);

// 设置脚本、语言、方向
hb_buffer_set_direction(buf, HB_DIRECTION_LTR);
hb_buffer_set_script(buf, HB_SCRIPT_LATIN);
hb_buffer_set_language(buf, hb_language_from_string("en", -1));

// 整形
hb_shape(font, buf, NULL, 0);

// 获取结果
unsigned int glyph_count;
hb_glyph_info_t *glyph_info = hb_buffer_get_glyph_infos(buf, &glyph_count);
hb_glyph_position_t *glyph_pos = hb_buffer_get_glyph_positions(buf, &glyph_count);

// 遍历字形
for (int i = 0; i < glyph_count; i++) {
    hb_codepoint_t glyphid = glyph_info[i].codepoint;

    int y_advance = glyph_pos[i].y_advance / 64.0;
    int x_offset = glyph_pos[i].x_offset / 64.0;
    int y_offset = glyph_pos[i].y_offset / 64.0;
    // 使用 FreeType 渲染 glyphid，在 (x + x_offset, y + y_offset) 位置绘制
}
```

## 4\.6 Pixman — 像素操作库

Pixman 是像素操作库，提供底层的像素级操作，包括合成、填充、变换等。它是 Cairo 和 Wayland 合成器的像素操作后端。

**Pixman 核心功能：**

- **图像合成**：支持 Porter\-Duff 合成操作（over、in、out、add 等）

- **图像变换**：缩放、旋转、仿射变换、双线性/双三次采样

- **渐变填充**：线性渐变、径向渐变、锥形渐变

- **图案填充**：重复图案、镜像图案

- **矩形操作**：矩形填充、矩形复制、矩形裁剪

- **滤镜**：卷积、模糊等图像滤镜

**移植要点：**

- Pixman 是纯 C 库，没有外部依赖

- 使用 Meson 或 Autotools 构建

- 有 MMX/SSE/NEON 等 SIMD 优化（x86\-64 上默认启用）

- 不需要任何内核支持

- 是 Cairo 的强制依赖

**支持的像素格式：**

- a8r8g8b8（32 位 ARGB，最常用）

- x8r8g8b8（32 位 RGB，无 Alpha）

- r5g6b5（16 位 RGB）

- a8（8 位 Alpha 遮罩）

- a1（1 位 Alpha）

- 等等

## 4\.7 Cairo — 2D 矢量图形

Cairo 是一个 2D 矢量图形库，提供高质量的抗锯齿 2D 渲染。它是 GTK、许多 Wayland 合成器和桌面应用的 2D 渲染后端。

**Cairo 核心功能：**

- **矢量图形绘制**：路径、贝塞尔曲线、矩形、圆形、多边形等

- **填充与描边**：纯色、渐变、图案填充和描边

- **文本渲染**：通过 FreeType \+ Fontconfig \+ HarfBuzz 渲染文本

- **坐标变换**：平移、旋转、缩放、仿射变换

- **合成操作**：Porter\-Duff 合成模式

- **多后端支持**：Image、Xlib、Wayland、PDF、SVG、PNG 等

**Cairo 后端：**

|后端|说明|用途|
|---|---|---|
|image|软件渲染到内存图像|通用、离线渲染|
|wayland|Wayland 窗口后端|Wayland 原生窗口|
|xcb / xlib|X11 后端|X11 窗口|
|pdf|PDF 文件输出|生成 PDF|
|svg|SVG 文件输出|生成 SVG|
|png|PNG 文件输出|生成 PNG 图片|
|gl|OpenGL 加速|硬件加速渲染|

**移植要点：**

- 依赖 Pixman（像素操作）、FreeType（字体）、Fontconfig（字体配置）、libpng（PNG 支持）

- 可以使用 Meson 或 Autotools 构建

- 初期只需要 image 后端（软件渲染）

- Wayland 后端需要 Wayland 客户端库（下一阶段）

- 是 GTK 的强制依赖

**基本使用示例：**

```c
#include <cairo.h>

// 创建图像表面（软件渲染）
cairo_surface_t *surface = cairo_image_surface_create(
    CAIRO_FORMAT_ARGB32, width, height);

// 创建 cairo 上下文
cairo_t *cr = cairo_create(surface);

// 绘制矩形
cairo_rectangle(cr, 10, 10, 100, 50);
cairo_set_source_rgb(cr, 0.8, 0.2, 0.2);
cairo_fill(cr);

// 绘制文本
cairo_set_source_rgb(cr, 0, 0, 0);
cairo_select_font_face(cr, "Sans", CAIRO_FONT_SLANT_NORMAL, 
                       CAIRO_FONT_WEIGHT_NORMAL);
cairo_set_font_size(cr, 16);
cairo_move_to(cr, 10, 80);
cairo_show_text(cr, "Hello, Cairo!");

// 销毁
cairo_destroy(cr);
cairo_surface_destroy(surface);
```

## 4\.8 libxkbcommon — 键盘布局

libxkbcommon 是键盘布局处理库，负责将键盘扫描码转换为字符，并处理键盘布局、组合键、死键等。它是 Wayland 输入处理的关键组件。

**为什么需要 libxkbcommon？**

evdev 上报的是按键码（key code），表示键盘上的物理按键位置。但用户需要的是字符（如 a、A、感叹号等）。键盘布局决定了哪个按键对应哪个字符。libxkbcommon 就是处理这个转换的库。

**XKB 核心概念：**

- **Keycode**：按键码，物理按键的编号（evdev 上报的 code）

- **Keysym**：键符号，按键对应的符号

- **Group**：键盘布局组（如英语、法语、德语，对应不同布局）

- **Level**：按键级别（如 Shift 按下时是 Level 2）

- **Modifier**：修饰键（Shift、Ctrl、Alt、Super 等）

- **Layout**：键盘布局（如 us、de、fr 等）

- **Compose**：组合键（多键组合生成特殊字符）

**移植要点：**

- libxkbcommon 是纯 C 库，依赖很少

- 需要 XKB 规则文件（通常在 /usr/share/X11/xkb/）

- XKB 规则文件来自 xkeyboard\-config 项目

- 使用 Meson 构建

- 是 libinput、Wayland compositor、GTK、Qt 等的依赖

**XKB 数据文件目录结构：**

```text
/usr/share/X11/xkb/
├── rules/          # 布局规则文件
│   └── evdev       # evdev 规则（最常用）
├── symbols/        # 符号映射（各语言布局）
│   ├── us          # 美式英语
│   ├── de          # 德语
│   └── fr          # 法语
├── keycodes/       # 按键码映射
│   └── evdev       # evdev 按键码
├── types/          # 按键类型定义
├── compat/         # 兼容性映射
└── geometry/       # 键盘几何形状（可选）
```

**基本使用示例：**

```c
#include <xkbcommon/xkbcommon.h>

// 创建上下文
struct xkb_context *ctx = xkb_context_new(XKB_CONTEXT_NO_FLAGS);

// 配置规则
struct xkb_rule_names names = {
    .rules = "evdev",
    .model = "pc105",
    .layout = "us",
    .variant = "",
    .options = ""
};

// 编译 keymap
struct xkb_keymap *keymap = xkb_keymap_new_from_names(
    ctx, &names, XKB_KEYMAP_COMPILE_NO_FLAGS);

// 创建状态
struct xkb_state *state = xkb_state_new(keymap);

// 处理按键事件
xkb_keycode_t keycode = event->code + 8;  // evdev + 8 = XKB
xkb_keysym_t keysym = xkb_state_key_get_one_sym(state, keycode);

// 更新修饰键状态
xkb_state_update_key(state, keycode, XKB_KEY_DOWN);
```

## 4\.9 libinput — 输入设备处理

libinput 是输入设备处理库，负责管理所有输入设备（键盘、鼠标、触摸板、触摸屏等），并提供统一的事件接口。它是 Wayland compositor 的标准输入处理库。

**libinput 核心功能：**

- **设备发现**：通过 udev 或路径发现输入设备

- **设备管理**：管理设备的打开、关闭、热插拔

- **事件处理**：读取 evdev 事件，处理后输出高级事件

- **指针加速**：鼠标移动的加速曲线

- **触摸板手势**：点击、滚动、捏合、滑动等手势识别

- **触摸屏处理**：多指触摸、手势识别

- **键盘处理**：按键重复、特殊键处理

- **绘图板支持**：压感、笔倾斜等

**移植要点：**

- 依赖 libudev（设备发现）、libxkbcommon（键盘布局）、mtdev（多点触摸）

- 使用 Meson 构建

- 需要 /dev/input/event\* 设备节点

- 需要 udev 或类似的设备管理机制

- 如果没有 udev，可以使用路径模式（直接指定设备路径）

**udev 替代方案：**

libinput 默认使用 udev 发现设备。如果 SpiritFoxOS 没有 udev，可以：

- **方案一**：移植 udev（或 eudev，独立版本）

- **方案二**：使用 libinput 的路径接口，手动指定设备路径

- **方案三**：实现一个简单的 udev 兼容层

**建议**：初期可以先不用 libinput，直接在 compositor 中读取 evdev 事件并处理。等基本功能跑通后，再移植 libinput。这样可以减少初期的依赖数量，更快看到效果。

# 阶段 5：Wayland 协议与 Compositor

## 5\.1 Wayland 协议核心概念

Wayland 是一个显示服务器协议，定义了客户端（应用程序）与合成器（Compositor）之间的通信方式。与 X11 不同，Wayland 本身只是协议规范，具体的实现由 Compositor 完成。

**Wayland 核心概念：**

- **Compositor（合成器）**：Wayland 显示服务器，负责管理显示输出、输入设备和窗口合成

- **Client（客户端）**：使用 Wayland 协议的应用程序

- **Surface（表面）**：客户端的可渲染区域，对应一个窗口或窗口的一部分

- **Buffer（缓冲区）**：客户端渲染的像素数据，通过 wl\_buffer 传递给合成器

- **Output（输出）**：物理显示器，提供分辨率、刷新率等信息

- **Seat（座位）**：输入设备的集合（键盘、指针、触摸等）

- **wl\_display**：Wayland 显示连接，客户端与合成器的核心连接对象

- **wl\_registry**：全局对象注册表，客户端通过它发现可用的全局对象

**Wayland 协议架构：**

**Wayland 协议特点：**

- **异步协议**：请求和事件都是异步的，不需要等待回复

- **对象模型**：协议基于对象，每个对象有 ID 和接口

- **请求（Request）**：客户端向合成器发送的调用

- **事件（Event）**：合成器向客户端发送的通知

- **共享内存传输**：像素数据通过共享内存（wl\_shm）或 DMA\-BUF 传递，不走 socket

- **协议可扩展**：通过协议扩展添加新功能（如 xdg\_shell、wp\_\* 等）

**核心协议对象：**

|对象|作用|
|---|---|
|wl\_display|核心连接对象，管理全局对象和同步|
|wl\_registry|全局对象注册表，发现和绑定全局对象|
|wl\_compositor|合成器全局对象，创建 surface 和 region|
|wl\_surface|可渲染的表面|
|wl\_buffer|像素数据缓冲区|
|wl\_output|显示输出（显示器）|
|wl\_seat|输入设备集合|
|wl\_pointer|指针（鼠标）设备|
|wl\_keyboard|键盘设备|
|wl\_touch|触摸设备|
|wl\_shm|共享内存缓冲区工厂|
|wl\_callback|回调对象，用于帧同步等|
|wl\_region|区域对象，用于损伤和输入区域|

## 5\.2 wayland\-scanner 与协议生成

Wayland 协议使用 XML 文件定义，通过 wayland\-scanner 工具生成 C 语言的绑定代码。这使得协议定义与实现分离，便于扩展和维护。

**协议 XML 文件结构：**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<protocol name="wayland">
  <copyright>...</copyright>

  <interface name="wl_compositor" version="4">
    <description summary="the compositor singleton">
      A compositor. ...
    </description>

    <request name="create_surface">
      <arg name="id" type="new_id" interface="wl_surface"/>
    </request>

    <request name="create_region">
      <arg name="id" type="new_id" interface="wl_region"/>
    </request>
  </interface>

  <interface name="wl_surface" version="4">
    <event name="enter">
      <arg name="output" type="object" interface="wl_output"/>
    </event>

    <request name="attach">
      <arg name="buffer" type="object" interface="wl_buffer" allow-null="true"/>
      <arg name="x" type="int"/>
      <arg name="y" type="int"/>
    </request>

    <request name="commit">
      <description summary="commit pending surface state">
        Surface state is double-buffered. ...
      </description>
    </request>
  </interface>
</protocol>
```

**wayland\-scanner 生成的文件：**

|生成目标|说明|用途|
|---|---|---|
|client\-header|客户端头文件|客户端应用使用|
|server\-header|服务端头文件|合成器使用|
|private\-code|协议实现代码|链接到客户端和服务端库|

**生成命令示例：**

```bash
# 生成客户端头文件
wayland-scanner client-header wayland.xml wayland-client-protocol.h

# 生成服务端头文件
wayland-scanner server-header wayland.xml wayland-server-protocol.h

# 生成实现代码
wayland-scanner private-code wayland.xml wayland-protocol.c
```

**核心库：**

- **libwayland\-client**：客户端库，提供 wl\_display、wl\_surface 等客户端 API

- **libwayland\-server**：服务端库，提供 wl\_display、wl\_resource 等服务端 API

- **libwayland\-cursor**：光标主题库，加载和管理光标

- **libwayland\-egl**：EGL 集成库，用于 OpenGL ES 渲染

**协议扩展：**

Wayland 核心协议只定义了基本功能，高级功能通过协议扩展实现：

- **xdg\_shell**：标准 shell 协议，定义窗口管理（标题、最小化、最大化等）

- **wl\_shell**：旧版 shell 协议（已废弃，被 xdg\_shell 取代）

- **wp\_viewporter**：视口扩展，支持缩放和裁剪

- **wp\_presentation**：显示时序信息

- **zwp\_linux\_dmabuf**：DMA\-BUF 缓冲区共享

- **zwp\_pointer\_constraints**：指针约束

- **zwp\_relative\_pointer**：相对指针

**重要**：xdg\_shell 是现代 Wayland 应用的标准窗口管理协议。几乎所有 Wayland 应用（GTK、Qt、SDL 等）都使用 xdg\_shell。实现 xdg\_shell 是 Compositor 能运行真实应用的关键。

## 5\.3 编写最小 Compositor

编写一个最小的 Wayland Compositor 是理解 Wayland 协议的最佳方式。下面介绍最小 Compositor 的基本结构。

**最小 Compositor 的组成部分：**

1. **Wayland 显示服务**：创建 wl\_display，监听客户端连接

2. **全局对象注册**：注册 wl\_compositor、wl\_output、wl\_seat 等全局对象

3. **渲染后端**：使用 DRM/KMS 或其他方式将内容显示到屏幕

4. **输入处理**：读取 evdev 事件，分发给焦点窗口

5. **窗口管理**：管理窗口的位置、大小、层级

6. **合成渲染**：将所有窗口的内容合成到帧缓冲

**基本代码结构：**

```c
#include <wayland-server.h>
#include <libdrm/drm.h>

struct my_compositor {
    struct wl_display *display;
    struct wl_event_loop *event_loop;

    // DRM/KMS
    int drm_fd;
    uint32_t crtc_id;
    uint32_t connector_id;
    drmModeModeInfo mode;

    // 输出
    struct wl_global *output_global;

    // 输入
    struct wl_global *seat_global;
    struct wl_keyboard *keyboard;
    struct wl_pointer *pointer;

    // 表面列表
    struct wl_list surfaces;
};

// 全局对象绑定回调
static void compositor_bind(struct wl_client *client, 
                            void *data, uint32_t version,
                            uint32_t id) {
    struct wl_resource *resource;
    resource = wl_resource_create(client, &wl_compositor_interface,
                                  version, id);
    wl_resource_set_implementation(resource, &compositor_impl,
                                   data, NULL);
}

int main(int argc, char *argv[]) {
    struct my_compositor *comp = calloc(1, sizeof(*comp));

    // 1. 创建 Wayland 显示
    comp->display = wl_display_create();
    comp->event_loop = wl_display_get_event_loop(comp->display);

    // 2. 初始化 DRM/KMS
    comp->drm_fd = open("/dev/dri/card0", O_RDWR);
    // ... 设置模式、创建帧缓冲 ...

    // 3. 注册全局对象
    wl_global_create(comp->display, &wl_compositor_interface,
                     4, comp, compositor_bind);

    wl_global_create(comp->display, &wl_output_interface,
                     3, comp, output_bind);

    wl_global_create(comp->display, &wl_seat_interface,
                     5, comp, seat_bind);

    // 4. 添加 Wayland socket
    wl_display_add_socket_auto(comp->display);

    // 5. 初始化输入设备
    init_input(comp);

    // 6. 进入主循环
    wl_display_run(comp->display);

    return 0;
}
```

**wl\_surface 实现要点：**

wl\_surface 是 Wayland 中最核心的对象之一。每个 surface 代表一个可渲染区域：

- **双缓冲状态**：surface 状态是双缓冲的，客户端修改后需要 commit 才生效

- **缓冲区附加**：客户端通过 attach 请求附加 wl\_buffer

- **损伤区域**：客户端通过 damage 请求标记需要重绘的区域

- **帧回调**：客户端可以请求帧回调，在绘制完成时得到通知

- **输入区域**：定义 surface 接收输入的区域

- **opaque 区域**：定义不透明区域，用于优化合成

**commit 处理流程：**

1. 客户端调用 wl\_surface\.commit\(\)

2. 合成器收到 commit 请求

3. 将 pending 状态应用到 current 状态

4. 如果有新的 buffer，更新 surface 的内容

5. 标记 surface 为需要重绘

6. 触发重新合成

7. 合成完成后发送 frame 回调事件

**学习资源**：推荐从 Wayland 官方的 "Wayland 入门" 教程和 weston（参考实现）的源码开始学习。weston 的 simple\-dmabuf\-drm 后端是最小 DRM 合成器的好例子。

## 5\.4 输出管理与帧回调

输出管理负责管理物理显示器，向客户端提供显示信息，并协调帧的绘制和显示时序。

**wl\_output 全局对象：**

wl\_output 向客户端提供显示器的信息：

- **geometry 事件**：物理尺寸、位置、子像素排列、制造商、型号

- **mode 事件**：支持的分辨率和刷新率

- **done 事件**：标记输出信息发送完成

- **scale 事件**：输出缩放因子（HiDPI 支持）

**帧回调机制：**

帧回调是 Wayland 实现流畅动画的关键机制：

1. 客户端请求 frame 回调（wl\_surface\.frame\(\)）

2. 合成器记录回调请求

3. 合成器在合适的时机（通常是 VBlank 后）触发回调

4. 客户端收到回调事件后绘制下一帧

5. 客户端 commit 新的缓冲区

6. 重复以上过程

这个机制确保客户端只在需要时才绘制，避免浪费 CPU/GPU 资源，同时保证帧率与显示器刷新率同步。

**页面翻转与 VBlank：**

- **页面翻转**：在 VBlank 期间切换显示的帧缓冲，避免画面撕裂

- **VBlank 事件**：DRM 提供 VBlank 事件通知，合成器可以等待 VBlank

- **帧调度**：合成器根据 VBlank 时机调度帧回调和重新合成

## 5\.5 输入设备集成

输入设备集成负责将 evdev 输入事件转换为 Wayland 输入事件，并分发给拥有焦点的客户端。

**wl\_seat 与输入设备：**

wl\_seat 是输入设备的抽象，表示一组输入设备（键盘、指针、触摸等）：

- **wl\_keyboard**：键盘设备，处理按键事件

- **wl\_pointer**：指针设备（鼠标），处理移动、按钮、滚轮事件

- **wl\_touch**：触摸设备，处理触摸事件

**键盘输入流程：**

1. evdev 上报按键事件

2. 合成器通过 libxkbcommon 将按键码转换为 keysym

3. 合成器确定键盘焦点窗口

4. 合成器向焦点客户端发送按键事件

5. 客户端收到事件后处理按键

**指针输入流程：**

1. evdev 上报指针移动事件

2. 合成器更新指针位置

3. 合成器检测指针进入/离开哪个 surface

4. 向进入的 surface 发送 enter 事件

5. 向离开的 surface 发送 leave 事件

6. 向焦点 surface 发送 motion 事件

7. 更新光标显示

**焦点管理：**

- **键盘焦点**：当前接收键盘输入的 surface，通常由点击窗口或窗口策略决定

- **指针焦点**：指针下方的 surface，随指针移动而变化

- **触摸焦点**：每个触摸点对应的 surface

**按键重复：**

按键自动重复由合成器控制：

- 客户端通过 wl\_keyboard\.repeat\_info 事件获取重复速率和延迟

- 客户端自己实现按键重复（Wayland 协议中，重复是客户端的责任）

- 合成器可以通过 repeat\_info 事件通知客户端重复参数

## 5\.6 Shell 协议与窗口管理

Shell 协议定义了窗口管理的语义，包括窗口标题、最小化、最大化、调整大小等。xdg\_shell 是现代 Wayland 的标准 Shell 协议。

**为什么需要 Shell 协议？**

Wayland 核心协议只定义了 surface（表面），但没有定义"窗口"的概念。窗口的概念（标题栏、边框、最小化/最大化按钮、调整大小等）由 Shell 协议定义。不同的 Shell 协议提供不同的窗口管理语义。

**xdg\_shell 核心对象：**

- **xdg\_wm\_base**：全局对象，创建 xdg\_surface 和 xdg\_positioner

- **xdg\_surface**：给 wl\_surface 添加窗口管理语义

- **xdg\_toplevel**：顶层窗口（普通应用窗口）

- **xdg\_popup**：弹出菜单、工具提示等临时窗口

- **xdg\_positioner**：定位器，用于定位弹出窗口

**xdg\_toplevel 功能：**

- **标题**：设置窗口标题

- **应用 ID**：设置应用程序标识符

- **最小化**：请求最小化窗口

- **最大化**：请求最大化/还原窗口

- **全屏**：请求进入/退出全屏

- **调整大小**：窗口边缘调整大小

- **窗口几何**：窗口内容区域的位置和大小

- **配置事件**：合成器向客户端建议窗口大小和状态

- **ack\_configure**：客户端确认配置事件

**窗口配置流程：**

1. 合成器决定窗口的新大小或状态

2. 合成器发送 configure 事件（带 serial）

3. 客户端收到 configure 事件

4. 客户端调整窗口内容大小

5. 客户端调用 ack\_configure 确认

6. 客户端 attach 新缓冲区并 commit

7. 合成器应用新的窗口状态

**窗口管理策略：**

合成器可以自由选择窗口管理策略：

- **浮动窗口管理**：窗口可以自由移动和调整大小（类似传统桌面）

- **平铺窗口管理**：窗口自动平铺排列（类似 i3、sway）

- **堆叠窗口管理**：窗口堆叠显示

- **动态窗口管理**：浮动和平铺结合

**里程碑**：当 Compositor 能运行 weston\-terminal 或其他简单的 Wayland 客户端，并能正确显示窗口和接收输入时，说明基本的 Wayland 协议实现是正确的。这是 Wayland 移植的最重要里程碑。

## 5\.7 层叠合成与损伤追踪

层叠合成是 Wayland Compositor 的核心功能，负责将所有窗口的内容合成到最终的屏幕图像。损伤追踪则是优化合成性能的关键技术。

**什么是合成（Compositing）？**

合成是将多个窗口的图像合并成一个最终屏幕图像的过程。在 Wayland 中，每个窗口渲染自己的内容到一个缓冲区，合成器负责将这些缓冲区按照正确的顺序和位置绘制到屏幕上。

**合成流程：**

1. 客户端 commit 新的缓冲区

2. 合成器标记该 surface 为脏（dirty）

3. 合成器调度一次重新合成

4. 合成器按从后到前的顺序绘制所有窗口

5. 每个窗口使用 alpha 混合（如果有透明度）

6. 最终图像呈现到屏幕

7. 触发帧回调，通知客户端可以绘制下一帧

**损伤追踪（Damage Tracking）：**

损伤追踪是一种优化技术，只重绘屏幕上变化的部分，而不是每次都重绘整个屏幕：

- **客户端损伤**：客户端通过 wl\_surface\.damage\(\) 标记 surface 上变化的区域

- **合成器损伤**：合成器计算屏幕上需要重绘的区域（所有变化窗口的并集）

- **部分重绘**：只重绘损伤区域，减少 GPU/CPU 工作量

- **减少带宽**：对于软件渲染，减少内存拷贝量

**合成方式：**

|方式|说明|性能|适用场景|
|---|---|---|---|
|软件合成|使用 CPU 进行像素合成（Pixman/Cairo）|较低|无 GPU 驱动、初期开发|
|OpenGL 合成|使用 OpenGL 进行硬件加速合成|高|有 GPU 驱动的系统|
|硬件平面|使用显示控制器的硬件平面（Overlay/Plane）|最高|支持多平面的硬件|

**软件合成实现要点：**

对于初期的 SpiritFoxOS，可以先实现软件合成：

- 使用 Pixman 库进行像素操作

- 每个窗口有自己的缓冲区（ARGB32 格式）

- 合成时按顺序将窗口内容绘制到屏幕缓冲区

- 支持 alpha 混合、变换、裁剪等

- 实现损伤追踪优化性能

**硬件平面（Overlay Plane）：**

现代显示控制器支持多个硬件平面，可以独立扫描输出不同的缓冲区：

- **主平面（Primary Plane）**：主要的显示平面

- **光标平面（Cursor Plane）**：专门用于鼠标光标，无需合成

- **覆盖平面（Overlay Plane）**：额外的叠加平面，用于视频等

使用硬件平面可以减少 GPU 工作量，降低功耗，提高性能。但需要硬件支持，且实现更复杂。

**建议**：初期先实现简单的软件合成（每次重绘整个屏幕），确保功能正确。然后逐步添加损伤追踪、硬件加速等优化。先跑起来，再优化。

## 6\.1 GTK 4 移植（Wayland 后端）

GTK 是最流行的 Linux 桌面 GUI 工具包之一，GNOME、Xfce 等桌面环境都基于 GTK。GTK 4 原生支持 Wayland。

**GTK 4 的 Wayland 后端：**

- **GDK Wayland 后端**：GTK 的底层抽象层（GDK）的 Wayland 实现

- **原生 Wayland 支持**：不需要 XWayland，直接使用 Wayland 协议

- **xdg\_shell 支持**：使用 xdg\_shell 协议进行窗口管理

- **CSD（客户端装饰）**：窗口边框和标题栏由客户端绘制

- **HiDPI 支持**：原生支持高 DPI 显示

**GTK 4 的依赖链：**

```text
GTK 4
├── GDK（底层抽象）
│   ├── Wayland 后端
│   │   ├── libwayland-client
│   │   ├── libwayland-cursor
│   │   └── xdg_shell 协议
│   └── 渲染后端
│       ├── OpenGL（通过 EGL）
│       └── Vulkan（可选）
├── Cairo（2D 矢量渲染）
├── Pango（文本布局）
│   ├── HarfBuzz（文本整形）
│   ├── FreeType（字体光栅化）
│   └── Fontconfig（字体配置）
├── GDK-Pixbuf（图像加载）
├── GLib（基础库）
│   ├── GObject（对象系统）
│   ├── GIO（I/O 抽象）
│   └── 数据结构
├── libepoxy（OpenGL 函数加载）
└── ...
```

**移植要点：**

- GTK 4 使用 Meson 构建系统

- 需要先移植所有依赖库（GLib、Cairo、Pango、HarfBuzz、FreeType、Fontconfig 等）

- Wayland 后端需要 libwayland\-client 和 xdg\_shell 协议

- OpenGL 渲染需要 Mesa 的 EGL 和 Wayland 平台支持

- 需要 D\-Bus 支持（用于设置、通知等）

- GTK 4 比 GTK 3 更容易移植，因为移除了很多旧的 X11 特定代码

## 6\.2 Qt 6 移植（Wayland 后端）

Qt 是另一个流行的跨平台 GUI 工具包，KDE、LXQt 等桌面环境基于 Qt。Qt 6 原生支持 Wayland。

**Qt 6 的 Wayland 支持：**

- **Qt Wayland 客户端**：Qt 应用可以作为 Wayland 客户端运行

- **Qt Wayland Compositor**：可以用 Qt 编写 Wayland 合成器

- **xdg\_shell 支持**：使用标准的 xdg\_shell 协议

- **CSD/SSD 支持**：支持客户端装饰和服务端装饰

- **平台插件**：通过 wayland 平台插件提供 Wayland 支持

**移植要点：**

- Qt 6 使用 CMake 构建系统

- 依赖较多，包括 libxkbcommon、libinput、fontconfig 等

- 需要 Mesa 的 EGL 和 OpenGL 支持

- Wayland 客户端支持相对容易移植

## 7\.5 D\-Bus 与系统服务

D\-Bus 是 Linux 桌面环境的标准进程间通信（IPC）机制，几乎所有桌面组件都依赖 D\-Bus。

**D\-Bus 的作用：**

- **系统总线（System Bus）**：系统级服务通信，如 NetworkManager、systemd、udisks 等

- **会话总线（Session Bus）**：用户会话内的应用通信，如通知、设置、媒体播放等

- **服务激活**：按需启动服务进程

- **信号机制**：发布/订阅式的事件通知

**桌面环境中依赖 D\-Bus 的组件：**

- **通知**：桌面通知（freedesktop\.org 通知规范）

- **设置守护进程**：存储和同步用户设置

- **网络管理**：NetworkManager 等网络配置工具

- **磁盘管理**：udisks 等磁盘和挂载管理

- **电源管理**：UPower 等电源状态管理

- **媒体播放**：MPRIS 媒体播放器控制接口

- **系统托盘**：StatusNotifierItem 托盘图标规范

**移植要点：**

- D\-Bus 守护进程（dbus\-daemon）需要移植

- 需要 /etc/dbus\-1/ 配置文件

- 需要 /run/dbus/ 运行时目录

- 系统总线需要以 root 身份运行

- 会话总线在用户登录时启动

- 依赖 libexpat（XML 解析）

**建议**：D\-Bus 是桌面环境的基础设施，但初期可以先跳过。先让基本的 Wayland 应用跑起来，再逐步添加 D\-Bus 支持。很多简单的 Wayland 应用不需要 D\-Bus。

# 调试与测试策略

调试 Wayland 桌面环境需要掌握多种工具和技术。以下是各层的调试方法和工具。

## 内核层调试

**DRM/KMS 调试：**

- **drm\_debug**：DRM 调试标志，可以启用各种 DRM 子系统的调试输出

- **modetest**：libdrm 自带的测试工具，测试模式设置和页面翻转

- **kmscube**：Mesa 自带的 OpenGL ES 测试程序

- **drm\-howto**：DRM 编程示例，包含基本的模式设置代码

- **QEMU \+ GDB**：使用 QEMU 的 GDB stub 调试内核

**输入子系统调试：**

- **evtest**：查看输入设备和事件

- **libinput debug\-events**：测试 libinput 的事件处理

- **input\-events**：简单的输入事件查看工具

## 用户态调试

**Wayland 调试：**

- **WAYLAND\_DEBUG**：环境变量，设置为 1 可以打印所有 Wayland 协议消息

- **wayland\-debug**：Wayland 协议调试工具

- **weston\-debug**：Weston 调试工具

- **wlr\-randr**：查看和设置输出配置（wlroots 合成器）

**使用示例：**

```bash
# 打印所有 Wayland 协议消息
WAYLAND_DEBUG=1 ./my-app

# 只打印客户端到服务端的消息
WAYLAND_DEBUG=client ./my-app

# 只打印服务端到客户端的消息
WAYLAND_DEBUG=server ./my-app
```

**图形调试：**

- **apitrace**：OpenGL 调用追踪

- **renderdoc**：图形调试器

- **EGL\_LOG\_LEVEL**：EGL 调试输出

- **LIBGL\_DEBUG**：Mesa 调试输出

## 测试策略

**分层测试：**

1. **内核层测试**：先确保 DRM/KMS 和 evdev 工作正常

2. **基础库测试**：测试 libdrm、Mesa 等基础库

3. **Wayland 协议测试**：使用 weston 等参考实现测试协议

4. **Compositor 测试**：运行简单的 Wayland 客户端

5. **应用测试**：运行 GTK/Qt 应用

6. **桌面环境测试**：运行完整的桌面环境

**关键测试程序：**

|测试程序|测试目标|来源|
|---|---|---|
|modetest|DRM/KMS 模式设置|libdrm|
|kmscube|OpenGL ES \+ KMS|Mesa|
|evtest|evdev 输入事件|evtest|
|weston\-terminal|Wayland 基本功能|Weston|
|weston\-info|Wayland 协议信息|Weston|
|gtk4\-demo|GTK 4 Wayland 后端|GTK|
|qmlscene|Qt Wayland 后端|Qt|

**调试技巧**：遇到问题时，先用 WAYLAND\_DEBUG=1 查看协议消息，确定问题出在客户端还是服务端。然后根据问题所在层级，使用对应的调试工具进一步定位。
